# Phase 2: ML target definition for recovery probability

## Scope

This document defines the Phase 2 machine-learning training target for the recovery decision layer without altering the Phase 1 rule engine or persistence model.

The goal is to model action-specific recovery probability for a failed payment, while keeping all features limited to data available before the recovery decision is made.

## Phase 1 facts already implemented

The current backend already defines the core recovery concepts needed for label design:

- Transaction state: `PENDING`, `SUCCESS`, `FAILED`, `RECOVERED`
- Payment attempt outcome: `SUCCESS` or `FAILED`
- Failure classification: `TEMPORARY_FAILURE`, `PAYMENT_METHOD_FAILURE`, `CUSTOMER_ACTION_REQUIRED`, `UNKNOWN_FAILURE`
- Recovery action types: `RETRY`, `ALTERNATE_METHOD`, `CUSTOMER_ACTION`, `ESCALATE`
- Recovery action lifecycle: `RECOMMENDED`, `EXECUTED`, `SUCCESS`, `FAILED`

Persisted model fields relevant to ML:

- `Transaction.id`, `amount`, `currency`, `customerId`, `status`, `createdAt`, `updatedAt`
- `PaymentAttempt.id`, `transactionId`, `paymentMethod`, `status`, `failureCategory`, `failureReason`, `attemptNumber`, `createdAt`
- `RecoveryAction.id`, `transactionId`, `attemptId`, `actionType`, `reason`, `status`, `createdAt`

The rule engine already creates a single `RecoveryAction` record for a failed attempt. The runtime then executes that action and may create a new payment attempt for `RETRY` and `ALTERNATE_METHOD`.

## One ML training example

A single ML training row represents:

1. The failed payment context at the instant the recovery decision is being made.
2. The candidate recovery action under evaluation.
3. The observed result of that action after execution.

In Phase 1 terms, the row is anchored to a failed `PaymentAttempt` and a recovery candidate created from that attempt:

- transaction snapshot before the decision
- attempt snapshot for the failed payment
- candidate `RecoveryAction.actionType`
- label derived after the action is executed

Conceptually:

```text
training_row = {
  transaction_context_before_decision,
  failed_attempt_context_before_decision,
  candidate_recovery_action,
  recovery_success
}
```

A row is not a whole transaction lifecycle. It is a single decision-event sample.

## Training-row definition

A training row corresponds to one failed payment attempt and one candidate recovery action considered for that attempt.

Required row semantics:

- `transaction_id`: the transaction being evaluated
- `attempt_id`: the failed attempt that triggered the recovery decision
- `candidate_action`: the recovery action type being scored, e.g. `RETRY`, `ALTERNATE_METHOD`, `CUSTOMER_ACTION`, or `ESCALATE`
- `features_before_decision`: all information available before the recovery decision, such as amount, currency, customer, payment method, failure category, reason, attempt count, and prior temporary-failure patterns
- `recovery_success`: binary outcome label defined below

This means the model is predicting the probability that a specific requested action succeeds when applied to a given failed payment situation.

## Prediction target: `recovery_success`

The prediction target is:

```text
recovery_success = 1  if the selected recovery action successfully recovered the payment
recovery_success = 0  if it did not recover the payment
```

This is intentionally action-specific and binary.

### Label logic

- For `RETRY` and `ALTERNATE_METHOD`, the runtime creates a follow-up `PaymentAttempt` and sets the transaction state to `SUCCESS` or `FAILED` accordingly.
- The recovery action record is then transitioned to `SUCCESS` or `FAILED` in Phase 1.
- Therefore, for these action types, label derivation is straightforward:

```text
recovery_success = 1 if RecoveryAction.status == 'SUCCESS'
recovery_success = 0 if RecoveryAction.status == 'FAILED'
```

- For `CUSTOMER_ACTION` and `ESCALATE`, the current Phase 1 implementation does not finalize a post-action success/failure signal. Those actions are executed without creating a new payment attempt and are left at `EXECUTED` in the current runtime.
- As a result, a value for `recovery_success` can only be defined conceptually for future workflow completion; it is not fully materialized by the present Phase 1 schema.

## Relationship between attempt, actions, execution, and outcome

The current data model makes the following relationship explicit:

1. One transaction can have many payment attempts.
2. One failed `PaymentAttempt` can have at most one recommended `RecoveryAction` in the current schema (`@@unique([attemptId])` in `RecoveryAction`).
3. The recommended action is selected from the rule engine based on the failed attempt context.
4. The action is executed by the recovery service.
5. The action outcome becomes one of:
   - a new payment attempt result for `RETRY` / `ALTERNATE_METHOD`
   - a terminal execution state for `CUSTOMER_ACTION` / `ESCALATE` in a later phase

This means the ML unit of observation is not the whole transaction, but the decision event:

```text
failed_attempt -> recommended_action -> execution -> observed outcome
```

The current runtime does not create multiple candidate actions per attempt. Phase 1 stores the chosen action only. For Phase 2, the training design should interpret the chosen action as the candidate action for that row. The broader model design can later support a richer action-space expansion, but the base training-row definition should remain one row per failed attempt / one action candidate.

## Reusable Phase 1 fields vs. new ML-only fields

### Reusable Phase 1 fields

These can be reused directly as features or label inputs without schema changes:

| Field | Source | Use in ML |
|---|---|---|
| `Transaction.amount` | `Transaction` | payment size feature |
| `Transaction.currency` | `Transaction` | currency context |
| `Transaction.customerId` | `Transaction` | user/customer pattern |
| `Transaction.status` | `Transaction` | pre-decision state, should be `FAILED` |
| `PaymentAttempt.paymentMethod` | `PaymentAttempt` | attempted method and alternate-method feasibility |
| `PaymentAttempt.failureCategory` | `PaymentAttempt` | primary failure pattern |
| `PaymentAttempt.failureReason` | `PaymentAttempt` | raw failure signal |
| `PaymentAttempt.attemptNumber` | `PaymentAttempt` | retry depth / history |
| `PaymentAttempt.createdAt` | `PaymentAttempt` | time-based features |
| `RecoveryAction.actionType` | `RecoveryAction` | candidate action feature / target dimension |
| `RecoveryAction.reason` | `RecoveryAction` | decision explanation text; can be used only if explicitly encoded |
| `RecoveryAction.createdAt` | `RecoveryAction` | model timing feature |
| `Transaction.paymentAttempts` history | runtime relationship | prior retry counts, historical failure pattern |

### Fields required for ML but not yet persisted in Phase 1

The current schema is sufficient to define the conceptual row and label, but it does not yet persist a dedicated ML training table. The following are operational requirements for the Phase 2 pipeline, not necessarily new business data fields:

- a persisted training-row snapshot that stores the feature vector exactly as used by the model
- a stable `candidate_action_id` / `decision_event_id` for traceability when multiple candidate actions are evaluated
- a `decision_made_at` timestamp explicitly tied to the prediction event
- a `recovery_outcome_confirmed_at` timestamp to distinguish pre-decision features from post-decision outcome timing
- an explicit `label_source` for action success/failure, especially for `CUSTOMER_ACTION` and `ESCALATE`

These are not duplicate fields; they are ML pipeline metadata for reproducible training data. They should be added in a dedicated ML layer or data warehouse, not by redesigning the Phase 1 payment schema.

### Important constraint

Do not create duplicate versions of existing Phase 1 fields such as a second `failureCategory` or second `status` column in the business schema. Reuse the existing persisted fields and derive a training snapshot from them.

## Leakage risks and guardrails

Features must only include information available before the recovery decision is made.

Potential leakage sources in the current model:

1. Using `RecoveryAction.status` as a feature
   - This is post-decision and should never be used as a predictive feature.
   - `status` is the result of the executed action, not a pre-decision signal.

2. Using the executed `PaymentAttempt` created after the recovery decision
   - `RETRY` and `ALTERNATE_METHOD` create a new attempt after the action is chosen.
   - Any features drawn from the post-execution attempt are leakage because they occur after the action is selected.

3. Using the final transaction status as a feature
   - For `RETRY` or `ALTERNATE_METHOD`, the transaction may be updated to `SUCCESS` or `FAILED` only after execution.
   - This is an outcome variable, not a feature.

4. Using decision text as a feature without explicit feature extraction
   - `RecoveryAction.reason` reflects the action chosen and therefore leaks the outcome indirectly.
   - It may be used only as a feature in a future modeling stage if it is treated as a text representation generated by the rule engine before the action execution and never includes post-execution outcome.

5. Including future payment history after the chosen action
   - Any attempt created after the decision, any later recovery actions, or any follow-up outcome are not eligible as predictors.

6. Using the actual executed action to define a feature for the same row
   - The row already includes the candidate action; that is part of the feature design, not a leakage variable.

The safe rule is:

```text
Only features from the state snapshot before the recovery decision may be included.
No feature may be derived from the chosen action's execution result.
```

## Final target definition

The Phase 2 label is:

```text
recovery_success
```

with definition:

```text
1 = the selected recovery action successfully recovered the payment
0 = the selected recovery action did not recover the payment
```

This label represents a binary success signal for one candidate action at one decision point.

## Schema gap note

The current Phase 1 schema supports the business entities and the rule-based decision flow, but it does not yet natively persist a dedicated ML training dataset or a final post-recovery success signal for all action types.

Specifically:

- `CUSTOMER_ACTION` and `ESCALATE` in the current codebase do not create a follow-up payment attempt and are not transitioned to `SUCCESS`/`FAILED` after execution, so the action-level success label is under-specified in current Phase 1 behavior.
- `RecoveryAction` enforces one action per failed attempt today, which matches the current rule-engine design but is a narrower action space than a broader ML feature set may eventually require.

This is a Phase 2 data-definition gap, not an instruction to redesign Phase 1 behavior.

## Implementation boundary for this task

This task does not train a model, expose an endpoint, or change the behavior of the existing recovery engine.

It only defines:

- what one ML sample is
- how the target is labeled
- how the candidate action maps to the outcome
- which existing fields are reusable
- which leakage risks must be avoided
- which ML data-pipeline gaps remain for a later implementation

## Summary

The correct ML target for the Phase 2 recovery engine is a binary action-specific label on a failed attempt decision event:

```text
recovery_success = 1 if candidate recovery action recovered the payment, else 0
```

The natural training row is:

```text
(failed payment attempt context at decision time, candidate action, observed success/failure of that action)
```

This design reuses the existing Phase 1 schema without changing current Phase 1 behavior, while explicitly documenting the remaining ML data capture gaps.
