# Phase 2: ML feature definition for recovery probability

## Purpose

This document defines the Phase 2 machine-learning feature set for the model:

```text
P(recovery_success | payment_context, candidate_recovery_action)
```

The feature set is intentionally limited to information that is available before the recovery decision is made.

This task does not train a model, expose a prediction endpoint, or modify the Phase 1 runtime behavior. It only defines which inputs can be used safely for future ML training.

## Feature design principles

1. Use only data available before the recovery decision.
2. Reuse existing Phase 1 persisted fields wherever possible.
3. Do not use any outcome variable or post-decision signal.
4. Do not add business/schema duplicates for ML-only fields unless they are explicitly marked as pipeline metadata, not business data.
5. Keep the first model simple and interpretable.
6. Prefer features that can be derived directly from `Transaction`, `PaymentAttempt`, and `RecoveryAction` records already persisted by Phase 1.
7. Treat the candidate action as part of the feature set, but never as a post-decision label or derived outcome.

## Core rule: leakage boundary

The following are forbidden in the feature set:

- `RecoveryAction.status`
- final `Transaction.status` after execution
- the next payment attempt created after the action
- future payment history after the prediction
- any information generated only after recovery execution
- `RecoveryAction.reason` used as raw text when it represents the selected action itself

The safe boundary is:

```text
Features = state snapshot before the recovery decision
Label = observed action success after execution
```

## Proposed feature table

### 1) Payment features

| Feature name | Source field/table | Data type | Meaning | Available at decision time | Leakage-safe | Transformation / encoding | Classification |
|---|---|---:|---|---|---|---|---|
| `transaction_amount` | `Transaction.amount` | Decimal / numeric | Monetary size of the payment | Yes | Yes | Convert to numeric amount in major currency units or keep as decimal | USE |
| `currency` | `Transaction.currency` | categorical string | Currency of the transaction | Yes | Yes | One-hot or learned embedding | USE |
| `payment_method_attempted` | `PaymentAttempt.paymentMethod` | categorical enum | Method used in the failed attempt | Yes | Yes | One-hot encoding | USE |
| `transaction_status_pre_decision` | `Transaction.status` | categorical enum | The transaction state before recovery is selected; should be `FAILED` | Yes | Yes | One-hot or constant-filtered; should remain `FAILED` in training rows | USE |
| `customer_id` | `Transaction.customerId` | string / categorical | Customer identifier available in current schema | Yes | Yes, if treated as a low-cardinality customer grouping only; not sensitive beyond model scope | Hashing / target encoding with caution | USE with caution |

Notes:
- `amount` and `currency` are strong, straightforward features and are already persisted.
- `payment_method_attempted` is essential because the recovery engine distinguishes `RETRY` and `ALTERNATE_METHOD` behavior by payment method.
- `customer_id` is the only customer context field available in the current schema. It may be used carefully, but it should not be expanded into more personal or sensitive features.

### 2) Failure features

| Feature name | Source field/table | Data type | Meaning | Available at decision time | Leakage-safe | Transformation / encoding | Classification |
|---|---|---:|---|---|---|---|---|
| `failure_category` | `PaymentAttempt.failureCategory` | categorical enum | Failure class from the current failed attempt | Yes | Yes | One-hot encoding | USE |
| `failure_reason_raw` | `PaymentAttempt.failureReason` | text string | Free-text reason supplied by the payment system | Yes | Yes, if treated as raw text only before action execution | Text normalization / hashed token features; not recommended in the minimum feature set | USE with caution |
| `has_failure_reason` | derived from `PaymentAttempt.failureReason` | binary | Whether a failure reason exists | Yes | Yes | Binary flag | USE |
| `failure_reason_length` | derived from `PaymentAttempt.failureReason` | numeric | Length of failure reason text | Yes | Yes | Numeric scaling | USE with caution |
| `failure_category_missing` | derived from `PaymentAttempt.failureCategory` | binary | Whether the failure category was null or absent | Yes | Yes | Binary flag | USE |

Notes:
- The current schema has direct failure metadata via `failureCategory` and `failureReason`.
- `failureReason` is useful only as a bounded raw signal or as a normalized text feature; it should not be treated as a direct category feature without careful encoding.
- A missing `failureCategory` should be considered a valid training signal, because the rule engine rejects invalid attempts but a historic dataset may have incomplete or missing category values.

### 3) Attempt and history features

| Feature name | Source field/table | Data type | Meaning | Available at decision time | Leakage-safe | Transformation / encoding | Classification |
|---|---|---:|---|---|---|---|---|
| `attempt_number` | `PaymentAttempt.attemptNumber` | integer | Current retry depth for the current transaction | Yes | Yes | Numeric feature | USE |
| `prior_attempt_count` | derived from `Transaction.paymentAttempts` before this attempt | integer | Total number of attempts before the current failed attempt | Yes | Yes | Numeric count | USE |
| `prior_failed_attempt_count` | derived from prior `PaymentAttempt` rows where `status = FAILED` | integer | Count of earlier failed attempts | Yes | Yes | Numeric count | USE |
| `prior_successful_attempt_count` | derived from prior `PaymentAttempt` rows where `status = SUCCESS` | integer | Count of earlier successful attempts | Yes | Yes | Numeric count | USE |
| `prior_temporary_failure_count` | derived from prior failed attempts with `failureCategory = TEMPORARY_FAILURE` | integer | Count of earlier temporary failures; used by the rule engine | Yes | Yes | Numeric count | USE |
| `prior_payment_method_counts` | derived from history of prior `paymentMethod` values | structured | Historical method distribution | Yes | Yes | Count vector or method-frequency features | USE with caution |
| `has_prior_recovery_action` | derived from earlier `RecoveryAction` rows on this transaction | binary | Whether this transaction already had a recovery action before current decision | Yes | Yes, if computed before the current action creation | Binary flag | USE |
| `prior_recovery_action_count` | derived from earlier `RecoveryAction` records on this transaction | integer | Number of recovery actions already suggested/used before the current decision | Yes | Yes | Numeric count | USE |
| `time_since_last_attempt` | derived from current attempt `createdAt` vs prior attempt `createdAt` | duration / numeric | Time gap between last failed attempt and current decision | Yes | Yes | Numeric seconds/minutes | FUTURE / optional |
| `time_since_first_attempt` | derived from transaction history timestamps | duration / numeric | Age of the payment journey | Yes | Yes | Numeric seconds/minutes | FUTURE / optional |

Notes:
- The current schema has enough information to compute the most useful pragmatic history features without introducing leakage:
  - `attempt_number`
  - `prior_failed_attempt_count`
  - `prior_temporary_failure_count`
  - counts by prior payment method
  - whether prior recovery actions exist
- These can all be derived from rows that exist before the current decision.
- Time-based features are feasible only if timestamps are aggregated carefully and only from pre-decision events.

### 4) Customer and payment-context features

| Feature name | Source field/table | Data type | Meaning | Available at decision time | Leakage-safe | Transformation / encoding | Classification |
|---|---|---:|---|---|---|---|---|
| `customer_id` | `Transaction.customerId` | string / categorical | Customer identifier already present in schema | Yes | Yes, but limited by privacy and cardinality | Hashing / grouping / target encoding | USE with caution |
| `currency` | `Transaction.currency` | categorical | Currency used by the transaction | Yes | Yes | One-hot encoding | USE |
| `transaction_age_hours` | derived from `Transaction.createdAt` and current decision time | numeric | Age of the transaction when recovery is evaluated | Yes | Yes | Numeric feature | FUTURE / optional |
| `payment_context_hash` | derived from transaction context | hash / categorical | A compact representation of payment context; not a new field | Yes | Yes | Hash or bucketization | FUTURE / optional |

Notes:
- The current schema contains only a minimal, still-usable customer context: `customerId`.
- No broader personal, device, behavioral, or consent-based features should be added without a clear schema and privacy review.
- `customerId` should be treated as a low-cardinality grouping signal only if needed, not as a source of sensitive personal data.

### 5) Candidate-action feature

| Feature name | Source field/table | Data type | Meaning | Available at decision time | Leakage-safe | Transformation / encoding | Classification |
|---|---|---:|---|---|---|---|---|
| `candidate_action_type` | `RecoveryAction.actionType` or the action being scored | categorical enum | The candidate recovery action currently under evaluation | Yes | Yes, because it is the action being modeled, not an outcome variable | One-hot encoding | USE |
| `candidate_action_is_retry` | derived from `candidate_action_type` | binary | Whether the action is `RETRY` | Yes | Yes | Binary flag | USE |
| `candidate_action_is_alternate_method` | derived from `candidate_action_type` | binary | Whether the action is `ALTERNATE_METHOD` | Yes | Yes | Binary flag | USE |
| `candidate_action_is_customer_action` | derived from `candidate_action_type` | binary | Whether the action is `CUSTOMER_ACTION` | Yes | Yes | Binary flag | USE |
| `candidate_action_is_escalate` | derived from `candidate_action_type` | binary | Whether the action is `ESCALATE` | Yes | Yes | Binary flag | USE |
| `reason_text` | `RecoveryAction.reason` | text string | Reason generated for the action | Yes | No, not safe if directly used as a feature because it encodes the policy decision itself | Avoid for the first model | DO NOT USE |

Notes:
- The candidate action is the model’s decision variable and is part of the prediction input.
- It is safe to encode the action type as a categorical feature or as separate binary flags.
- `reason_text` should not be used in the first model because it is policy-generated and may mirror the chosen action, which creates leakage risk and weakens generalization.

## Leakage exclusions

The following features are explicitly excluded:

| Feature | Why excluded |
|---|---|
| `RecoveryAction.status` | This is the post-decision outcome / execution label and not pre-decision context |
| Final `Transaction.status` after action execution | It is part of the observed outcome, not an input |
| Recovery attempt created after action execution | It occurs after the decision and is not available at prediction time |
| Post-decision payment history | Future data is out-of-scope and violates causal ordering |
| `RecoveryAction.reason` | Policy text tied to the chosen action; can encode the decision itself |
| action outcome signals for `CUSTOMER_ACTION` and `ESCALATE` | These are not yet persisted in Phase 1 and may be under-specified |

The general exclusion rule is:

```text
If a field is created by or changed because of the recovery action execution, it is not a valid feature.
```

## Required transformations / encodings

For the first model, the minimum practical encoding strategy is:

1. Numeric features
   - `amount`: convert to a numeric scalar, e.g. normalized amount or log amount if needed
   - `attempt_number`: integer feature
   - `prior_failed_attempt_count`: integer feature
   - `prior_temporary_failure_count`: integer feature
2. Categorical features
   - `currency`: one-hot or learned embedding
   - `payment_method_attempted`: one-hot encoding
   - `failure_category`: one-hot encoding
   - `candidate_action_type`: one-hot encoding or a single categorical embedding
3. Binary indicators
   - `has_failure_reason`
   - `candidate_action_is_retry`
   - `candidate_action_is_alternate_method`
   - `candidate_action_is_customer_action`
   - `candidate_action_is_escalate`
4. Text feature handling
   - `failureReason` should be deferred until a clear text pipeline is defined; it is optional and should not be in the first minimal model

## Current-schema limitations

The current Phase 1 schema has enough information to calculate many useful features, but it is still limited in a few ways:

1. No dedicated feature table or training snapshot
   - The schema does not yet persist a curated ML training-row artifact.
2. No explicit action decision timestamp
   - There is no persisted time of prediction or time of action recommendation separate from record creation.
3. No standardized outcome tracking for all action types
   - `CUSTOMER_ACTION` and `ESCALATE` do not presently create a follow-up payment attempt or finalize a success/failure signal.
4. Only minimal historical structure is available
   - The schema supports transaction and attempt history, but not richer features such as customer clusters or segmentation.
5. No easy multi-candidate action evaluation
   - Phase 1 stores one recommended action per failed attempt. That is enough for the first single-action model, but not for a richer action-space model.

## Recommended minimum feature set for the first model

The first model should use the smallest feature set that is clearly safe and useful:

- `transaction_amount`
- `currency`
- `payment_method_attempted`
- `failure_category`
- `has_failure_reason`
- `attempt_number`
- `prior_failed_attempt_count`
- `prior_temporary_failure_count`
- `candidate_action_type`

Optional but useful:

- `customer_id` with careful encoding or bucketing
- `prior_recovery_action_count`
- `prior_payment_method_counts`

This is a practical minimum because all of these are already available in the existing schema and are derived only from pre-decision data.

## Features explicitly deferred to a future version

These features should not be part of the first model:

- `failure_reason_raw` as a direct text field
- `time_since_last_attempt`
- `transaction_age_hours`
- `customer_id` as a raw high-cardinality identifier without controlled encoding
- rich historical sequences or per-customer aggregates beyond the current schema
- any feature derived from post-execution attempts or statuses
- any text feature based on `RecoveryAction.reason`

These are valuable only after the schema and data pipeline are expanded, or when a dedicated ML dataset and proper feature-engineering pipeline exist.

## Summary

The feature set for Phase 2 should be grounded in the current Phase 1 schema and should only include signal available before the recovery decision. The strongest and safest minimum feature set is:

```text
amount, currency, failed payment method, failure category, failure reason presence, attempt number, prior failed count, prior temporary failure count, candidate action type
```

This set is consistent with the business model, avoids leakage, and requires no runtime behavior change to the Phase 1 code.
