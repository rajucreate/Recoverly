# Phase 2: Prediction input/output contract for recovery probability

## 1. Prediction objective

The model predicts the probability that a candidate recovery action successfully recovers a failed payment.

The conceptual prediction is:

```text
P(recovery_success | payment_context, candidate_recovery_action)
```

Where:

- `payment_context` is the pre-decision state of the payment transaction and failed attempt
- `candidate_recovery_action` is the specific action being evaluated, e.g. `RETRY`, `ALTERNATE_METHOD`, `CUSTOMER_ACTION`, or `ESCALATE`
- `recovery_success` is the binary label described in the earlier Phase 2 target definition

This is intentionally a one-action-at-a-time prediction, not a single transaction-level decision.

## 2. Input contract

### 2.1 Core input semantics

The system evaluates a single candidate recovery action against the payment context.

Conceptually:

```text
input = {
  payment_context: {...},
  candidate_action_type: "RETRY" | "ALTERNATE_METHOD" | "CUSTOMER_ACTION" | "ESCALATE"
}
```

### 2.2 Approved feature set from 6.1.2

The model input must use only the approved features from the Phase 2 feature definition document.

#### A. Raw business fields

These are existing persisted Phase 1 fields:

- `transaction_amount`: numeric amount from `Transaction.amount`
- `currency`: string enum from `Transaction.currency`
- `payment_method_attempted`: enum from `PaymentAttempt.paymentMethod`
- `failure_category`: enum from `PaymentAttempt.failureCategory`
- `has_failure_reason`: derived from `PaymentAttempt.failureReason`
- `attempt_number`: integer from `PaymentAttempt.attemptNumber`
- `prior_failed_attempt_count`: derived from prior failed payment attempts
- `prior_temporary_failure_count`: derived from prior failed attempts where `failureCategory = TEMPORARY_FAILURE`
- `candidate_action_type`: enum of the target recovery action being scored

#### B. Model-ready transformed fields

These are the same concepts represented in a format suitable for the model.

```json
{
  "transaction_amount": 5000.00,
  "currency": "INR",
  "payment_method_attempted": "UPI",
  "failure_category": "TEMPORARY_FAILURE",
  "has_failure_reason": true,
  "attempt_number": 1,
  "prior_failed_attempt_count": 0,
  "prior_temporary_failure_count": 0,
  "candidate_action_type": "RETRY"
}
```

#### C. Categorical encodings

The model must encode categorical fields before scoring, for example:

- `currency`: one-hot or learned embedding
- `payment_method_attempted`: one-hot encoding
- `failure_category`: one-hot encoding
- `candidate_action_type`: one-hot encoding or a categorical embedding

These encodings are transformation details, not the raw business contract.

#### D. Numerical fields

The model-ready numerical fields are:

- `transaction_amount`
- `has_failure_reason` (binary numeric 0/1)
- `attempt_number`
- `prior_failed_attempt_count`
- `prior_temporary_failure_count`

These are feature values that may be normalized before model scoring.

### 2.3 Input object shape

The conceptual input contract should be represented as:

```json
{
  "transaction_amount": 5000.0,
  "currency": "INR",
  "payment_method_attempted": "UPI",
  "failure_category": "TEMPORARY_FAILURE",
  "has_failure_reason": true,
  "attempt_number": 1,
  "prior_failed_attempt_count": 0,
  "prior_temporary_failure_count": 0,
  "candidate_action_type": "RETRY"
}
```

The model service may also receive metadata for tracing, but the prediction model itself must consume only the model-ready feature vector above.

## 3. Output contract

The model returns a prediction for the candidate action.

Minimum required output:

```json
{
  "candidate_action_type": "RETRY",
  "recovery_probability": 0.72,
  "model_version": "phase2-recovery-v1"
}
```

### 3.1 Required fields

- `candidate_action_type`: the action being scored
- `recovery_probability`: probability in the range `[0, 1]`
- `model_version`: string identifying model/build version used to produce the score

### 3.2 Optional but recommended metadata

For operational clarity and debugging, the system may also expose:

- `predicted_at`: ISO-8601 timestamp when the model prediction was generated
- `feature_version`: version identifier for the feature set used
- `confidence`: optional statistical confidence metric, distinct from `recovery_probability`

Important: `confidence` is not the same as `recovery_probability`.

## 4. Multi-action scoring strategy

The model evaluates one candidate action at a time, but the system can score all legal actions for the same payment context.

### 4.1 Multi-action evaluation pattern

For a given failed payment context `X`, the system should create four candidate requests:

- `X + RETRY`
- `X + ALTERNATE_METHOD`
- `X + CUSTOMER_ACTION`
- `X + ESCALATE`

Then score each candidate independently.

Conceptually:

```text
for action in [RETRY, ALTERNATE_METHOD, CUSTOMER_ACTION, ESCALATE]:
  input = { payment_context: X, candidate_action_type: action }
  result = model.predict(input)
  scores.append({ action, probability: result.recovery_probability })
```

Result example:

```json
[
  { "action": "RETRY", "probability": 0.72 },
  { "action": "ALTERNATE_METHOD", "probability": 0.41 },
  { "action": "CUSTOMER_ACTION", "probability": 0.18 },
  { "action": "ESCALATE", "probability": 0.09 }
]
```

### 4.2 Deterministic ordering and tie-breaking

The ordered candidate list should be deterministic:

```text
RETRY -> ALTERNATE_METHOD -> CUSTOMER_ACTION -> ESCALATE
```

This order should be used when returning a ranked list or when two probabilities are numerically equal.

Tie-breaking rule:

1. Higher probability wins.
2. If probabilities are equal, use the fixed action ordering above.
3. If the model is unavailable, the system should defer to the existing rule engine rather than producing a custom tie-breaker outcome.

## 5. Probability semantics

`recovery_probability` means:

```text
the probability that this specific candidate recovery action will successfully recover the payment, given the payment context and the action being evaluated
```

This must be a value in the range:

```text
0.0 <= recovery_probability <= 1.0
```

### 5.1 Valid probability range

- `0.0` means the action is predicted to almost certainly fail to recover the payment
- `1.0` means the action is predicted to almost certainly succeed
- values outside `[0, 1]` are invalid

If the model outputs a value outside the range, the prediction should be treated as invalid and the system must handle it as an error or fallback condition.

## 6. Model confidence vs recovery probability

This is a critical distinction.

### 6.1 `recovery_probability`

`recovery_probability` is the model’s estimate of the success chance for the current action.

This is the business prediction being made.

### 6.2 `confidence`

`confidence` is a separate statistical concept, such as:

- model uncertainty
- prediction spread
- calibration quality
- probability margin from a threshold

It is not the same as the action success probability.

Examples:

- `recovery_probability = 0.72`
- `confidence = 0.84`

These are not interchangeable. A model can predict a recovery probability of `0.72` with low or high confidence depending on calibration and feature coverage.

The system should avoid mixing the two in business logic unless explicitly required for monitoring or model-quality reporting.

## 7. Validation rules

A prediction request is valid only if:

- all required features are present
- categorical values are recognized values
- numerical values are numeric and finite
- `candidate_action_type` is one of the supported values
- the input is from the state snapshot before the decision

### 7.1 Required feature validation

Required input features:

- `transaction_amount`
- `currency`
- `payment_method_attempted`
- `failure_category`
- `has_failure_reason`
- `attempt_number`
- `prior_failed_attempt_count`
- `prior_temporary_failure_count`
- `candidate_action_type`

Any missing required field should trigger a validation error or fallback to the rule engine, depending on operational policy.

### 7.2 Missing-feature handling

If a required feature is missing:

1. reject the prediction request as invalid if the feature is essential to the model
2. or fallback to rule-engine decision if the model is unavailable or the request is incomplete

For the first design, the safer behavior is:

```text
Missing required feature => do not score the request with ML; fallback to the existing Phase 1 rule engine.
```

### 7.3 Invalid prediction handling

If the model returns:

- NaN
- infinity
- probability outside `[0,1]`
- unsupported action type
- unusable feature vector

then the prediction must be rejected and treated as a model failure, not as a valid business recommendation.

## 8. Error and fallback behavior

If the model is unavailable, misconfigured, or returns invalid output, the system must preserve the existing Phase 1 rule engine behavior.

The fallback policy should be:

```text
Model unavailable / invalid => use the existing RecoveryDecisionEngine recommendation and current rule-based action selection.
```

This ensures Phase 1 runtime behavior stays unchanged and all existing recovery semantics continue to work.

Fallback behaviors:

- model error logs the issue and records the fallback path
- rule engine continues to choose the action according to Phase 1 logic
- no model output is used in the live decision path if the model fails validation

## 9. Model versioning

The model output should include version metadata so training and production can be tracked.

Minimum version fields:

- `model_version`: e.g. `phase2-recovery-v1`
- `feature_version`: optional version of the feature pipeline

Example:

```json
{
  "candidate_action_type": "RETRY",
  "recovery_probability": 0.72,
  "model_version": "phase2-recovery-v1",
  "feature_version": "phase2-feature-v1",
  "predicted_at": "2026-08-25T10:00:00.000Z"
}
```

Versioning is necessary for:

- reproducibility
- monitoring drift
- comparing candidate model behavior
- troubleshooting production issues

```json
{
  "transaction_amount": 5000.0,

  "payment_method_attempted": "UPI",
  "failure_category": "TEMPORARY_FAILURE",
  "has_failure_reason": true,
  "attempt_number": 1,
  "prior_failed_attempt_count": 0,

```

### Candidate evaluation

```json
[
  {
    "candidate_action_type": "RETRY",
    "recovery_probability": 0.72,
    "model_version": "phase2-recovery-v1"
  },
  {
    "candidate_action_type": "ALTERNATE_METHOD",
    "recovery_probability": 0.41,
    "model_version": "phase2-recovery-v1"
  },
  {
    "candidate_action_type": "CUSTOMER_ACTION",
    "recovery_probability": 0.18,

    "model_version": "phase2-recovery-v1"
  }
```

This array is a ranked score set for the same payment context. The ranking is deterministic based on probability and then fixed action ordering.

## 11. Compatibility with the existing Phase 1 recovery engine

The Phase 1 engine already decides based on:

- failure category
- previous temporary-failure count
- payment method behavior

This design preserves that engine intact.

The ML contract sits beside it as a future decision-support component:

- it does not replace the rule engine
- it does not change runtime execution or persistence behavior
- it does not alter `RecoveryAction` creation or execution semantics
- it only provides a model scoring interface that can be used later for ranking or recommendation

This is a compatibility-safe design: if the model fails, the system continues using the rule engine exactly as it does today.

## Summary

The prediction contract is a single-action scoring interface:

```text
Input = payment context + candidate action
Output = probability that the candidate action succeeds
```

The minimum safe output object is:

```json
{
  "candidate_action_type": "RETRY",
  "recovery_probability": 0.72,
  "model_version": "phase2-recovery-v1"
}
```

The multi-action flow scores each candidate separately and returns a deterministic ranked list, while the fallback policy remains the existing Phase 1 `RecoveryDecisionEngine`.
