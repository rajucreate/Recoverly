# Phase 2: ML vs Rule Engine integration policy

## 1. Architecture

The architecture is intentionally layered and must remain non-overlapping.

```text
Failed Payment
  -> Failure Classification
  -> RecoveryDecisionEngine (Phase 1)
  -> Recovery Action
  -> RecoveryExecutionService (Phase 1)
```

For Phase 2, the design adds a recommendation layer without changing the execution model:

```text
Failed Payment
  -> Feature Construction
  -> ML scoring for candidate actions
  -> Decision Policy
  -> Selected Recovery Action
  -> Existing RecoveryExecutionService
```

The responsibilities are:

- ML model: recommend action-specific success probability
- Decision policy: rank, filter, validate, and choose among recommendations
- Phase 1 RecoveryDecisionEngine: current deterministic business rule engine
- RecoveryExecutionService: single runtime execution engine for all recovery actions

This is the key rule:

```text
ML MODEL = recommendation
DECISION POLICY = decision
PHASE 1 EXECUTION ENGINE = execution
```

No model is allowed to directly execute a recovery action.

## 2. Phase 1 flow (source of truth)

The current implementation already defines the Phase 1 flow:

1. A failed payment attempt is created via `TransactionService.createPaymentAttempt`.
2. The failed attempt includes a `failureCategory` and optional `failureReason`.
3. `RecoveryDecisionEngine.decide({ failureCategory, previousTemporaryFailureCount })` chooses a recovery action.
4. The chosen action is persisted as a `RecoveryAction` with `status = RECOMMENDED`.
5. `RecoveryExecutionService.execute(...)` loads that action and transitions it to `EXECUTED`.
6. For `RETRY` and `ALTERNATE_METHOD`, a new payment attempt is created and the transaction status is updated to `SUCCESS` or `FAILED`.
7. For `CUSTOMER_ACTION` and `ESCALATE`, the action is marked executed without creating a follow-up attempt.
8. The actual execution semantics remain entirely in the existing Phase 1 service.

This flow is what must remain authoritative for all runtime execution.

## 3. Phase 2 flow

Phase 2 introduces an advisory ML layer before the existing selection/decision step.

```text
Failed payment attempt
  -> build payment context from transaction + attempt + history
  -> score each candidate action using the model
  -> produce probabilities for RETRY, ALTERNATE_METHOD, CUSTOMER_ACTION, ESCALATE
  -> decision policy ranks and filters predictions
  -> selected action is passed to the existing recovery action creation / execution flow
  -> RecoveryExecutionService executes the chosen action exactly as it does today
```

Important: the rule engine and execution service continue to own the final business decision and database state transitions.

The model does not create a `RecoveryAction` record directly. The model does not transform the status of a transaction. The model does not call payment-provider logic.

## 4. Responsibility boundaries

### 4.1 ML model responsibility

The ML model is responsible for:

- taking payment context + candidate action
- producing a probability for that candidate
- returning model metadata such as version
- returning a probability score in the range `[0,1]`

The model is not responsible for:

- selecting the final action under business rules
- enforcing safety constraints
- checking retry limits
- calling execution APIs
- persisting business state
- mutating transaction status

### 4.2 Decision policy responsibility

The decision policy is responsible for:

- ranking the candidate action probabilities
- validating the candidate actions against the current business state
- enforcing rule constraints such as retry limits and alternate-method compatibility
- rejecting or downgrading unsafe candidates
- resolving ties deterministically
- selecting the final action to recommend or to pass through the existing rule path
- falling back to the Phase 1 rule engine when necessary

### 4.3 Phase 1 rule engine responsibility

The existing `RecoveryDecisionEngine` remains the deterministic fallback and compatibility path.

It is responsible for:

- mapping failure category to action type
- applying retry-limit logic
- honoring business policies already in production
- producing the persisted `RecoveryAction` row

### 4.4 RecoveryExecutionService responsibility

`RecoveryExecutionService` remains the single execution engine.

It is responsible for:

- validating the transaction is in a failed state
- validating the target recovery action belongs to the transaction
- transitioning action state (`RECOMMENDED` -> `EXECUTED` -> success/failure)
- creating a new recovery attempt for `RETRY` and `ALTERNATE_METHOD`
- calling the payment provider for actual recovery attempts
- updating transaction state as Phase 1 already does

No second execution path is allowed for ML decisions.

## 5. ML recommendation rules

The model produces recommendations in this shape:

```json
[
  { "action": "RETRY", "probability": 0.82 },
  { "action": "ALTERNATE_METHOD", "probability": 0.64 },
  { "action": "CUSTOMER_ACTION", "probability": 0.41 },
  { "action": "ESCALATE", "probability": 0.18 }
]
```

The ML output is advisory only.

A recommendation must not be treated as an execution decision automatically.

Rules:

1. Model returns action-specific probabilities, not direct execution commands.
2. The model is allowed to provide a ranked recommendation set.
3. The decision policy selects the final action using established rules plus safety constraints.
4. The execution layer still executes only the selected action after policy approval.
5. The model may be used as a ranking signal, but not as a bypass for Phase 1 logic.

## 6. Decision-policy rules

The decision policy is the boundary between recommendation and execution.

### 6.1 Ranking

The policy ranks candidate actions by:

- model probability descending
- then deterministic tie-break ordering

Recommended ordering:

```text
RETRY -> ALTERNATE_METHOD -> CUSTOMER_ACTION -> ESCALATE
```

This keeps the ordering deterministic and stable.

### 6.2 Candidate validation

Before accepting a candidate action, the policy checks:

- the candidate action is supported by the model contract
- the action is valid for the payment context
- the action is allowed under the current business state
- the action has not already been executed
- the action is not blocked by safety constraints

### 6.3 Safety constraints

Safety constraints include:

- respect retry limits already encoded in `RecoveryDecisionEngine`
- do not allow repeated retries beyond Phase 1 policy bounds
- do not allow `ALTERNATE_METHOD` to use the same payment method as the failed attempt
- do not allow an action that conflicts with the transaction state
- do not allow ML to bypass transaction validation rules

### 6.4 Confidence and uncertainty handling

`recovery_probability` is not the same as model confidence.

Policy should treat model confidence as a monitoring or logging concern, not a direct execution criterion in the first integration design.

If insufficient confidence is considered a policy threshold in the future, it must only be used in a gated decision layer and must still fallback to Phase 1 when necessary.

### 6.5 Tie handling

Tie-breaking should be deterministic:

1. highest probability wins
2. equal probability => prior fixed enumerated order wins
3. if the selected action violates a safety constraint, skip it and continue to the next valid action
4. if no valid action remains, fallback to Phase 1 rule engine

## 7. Fallback matrix

The fallback policy is explicit and conservative.

| Condition | Behavior | Rule engine used? | Action blocked? | Escalation? |
|---|---|---|---|---|
| Model unavailable | Ignore ML output and use Phase 1 rule engine | Yes | No | No |
| Prediction timeout | Ignore ML output and use Phase 1 rule engine | Yes | No | No |
| Invalid prediction structure | Reject ML output and fall back | Yes | No | No |
| Probability outside `[0,1]` | Reject score and fall back | Yes | No | No |
| Missing required feature | Reject score and fall back | Yes | No | No |
| Unsupported candidate action | Reject score and fall back | Yes | No | No |
| Safety constraint violation | Reject candidate, continue ranking or fall back | Yes | Yes for candidate | Optional if required by existing policy |
| Insufficient model confidence | Use rule engine if confidence threshold is configured and not met | Yes | No | No |
| All candidate actions invalid | Use Phase 1 rule engine as final default | Yes | Yes, all ML candidates blocked | No interrupt to existing engine |

The principle is simple:

```text
If ML cannot produce a valid, safe, business-consistent recommendation, use the Phase 1 rule engine.
```

## 8. Safety constraints

The Phase 1 business logic already includes critical safety checks:

- transaction must be in `FAILED` state before recovery execution
- action must belong to the transaction
- action must be in `RECOMMENDED` state before execution
- `RETRY` uses the original payment method
- `ALTERNATE_METHOD` requires a different payment method
- a duplicate execution for the same action is rejected
- the retry limit from `RecoveryDecisionEngine` remains authoritative

The ML decision policy must not bypass these checks.

Additional Phase 2 safety constraints for the decision layer:

- only use supported action types
- only use valid probability outputs
- do not allow one model failure to create a new execution path
- never allow a model decision to skip transaction validation
- if any safety check fails, the candidate is discarded or fallback occurs

## 9. Rollback strategy

The integration should support a feature flag concept in a future Phase 2 implementation, but it is not implemented in this task.

The rollout policy should be:

1. Keep Phase 1 rule engine as default path.
2. Add a configuration switch for ML recommendation mode.
3. If the switch is off, the system always uses the existing `RecoveryDecisionEngine`.
4. If the switch is on but the model fails validation, fallback immediately to the rule engine.
5. If the flag is disabled at runtime, the model path is bypassed completely.

The document-level design is:

```text
ML feature flag = off by default
Phase 1 rule engine = always active and authoritative
```

This way, rollback is immediate and requires no application code change beyond configuration.

## 10. Audit requirements

For every intelligent decision, the system should eventually record:

- `decision_timestamp`
- `transaction_id`
- `attempt_id`
- `candidate_action_type`
- `model_version`
- `feature_version`
- `prediction_scores`
- `selected_action`
- `fallback_reason`, if any
- `rule_engine_used` flag
- `decision_policy_version`, if introduced later

This is audit/observability metadata only. It does not replace the Phase 1 business state or execution records.

The Phase 1 execution remains the source of truth for actual recovery execution and outcome persistence.

## 11. Example decision scenarios

### Scenario A: model is healthy

Given a failed payment with `TEMPORARY_FAILURE` and no prior retries:

```text
RETRY = 0.82
ALTERNATE_METHOD = 0.64
CUSTOMER_ACTION = 0.41
ESCALATE = 0.18
```

Policy selection:

- the probabilities are valid
- no safety constraint is violated
- `RETRY` is highest and valid
- selected action = `RETRY`
- then the existing `RecoveryExecutionService` executes it

### Scenario B: retry limit would be violated

The model suggests `RETRY` with a high score, but Phase 1 policy says the retry limit has been reached.

Behavior:

- policy rejects `RETRY`
- policy applies existing retry-limit rule
- fallback path or rule-engine action resolves to `ESCALATE`
- execution remains inside the Phase 1 engine

### Scenario C: model returns invalid score

The model returns:

```text
RETRY = 1.42
ALTERNATE_METHOD = 0.55
```

Behavior:

- invalid probability range triggers rejection
- model output is discarded
- rule engine is used
- no direct action is executed by ML

### Scenario D: model unavailable

Model service times out or is unreachable.

Behavior:

- no ML decision is used
- Phase 1 `RecoveryDecisionEngine` chooses the action
- execution uses the same Phase 1 service as before

## Summary

The intended integration pattern is:

```text
ML recommendations inform the decision, but Phase 1 rules and execution remain authoritative.
```

The final design principle is:

```text
Never let model output bypass the existing Phase 1 RecoveryDecisionEngine or RecoveryExecutionService.
```

This preserves compatibility, safety, and predictability while allowing future ML experimentation without changing business behavior.
