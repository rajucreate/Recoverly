# Phase 2: Model evaluation and baseline comparison strategy

## 1. Evaluation objective

The objective is to determine whether the future intelligent recovery model improves the recovery outcome over the existing Phase 1 rule-based recovery system.

The design must evaluate the model before any production integration is considered.

The comparison is always against the current business logic:

```text
Rule-based baseline = current RecoveryDecisionEngine + current RecoveryExecutionService
```

The key question is:

```text
Does the intelligent policy improve recovery success over the Phase 1 rule engine on the same payment scenarios?
```

## 2. Baseline definition

The baseline is the current Phase 1 implementation, exactly as it exists today.

Baseline sources of truth:

- `TransactionService.createPaymentAttempt(...)`
- `RecoveryDecisionEngine.decide({ failureCategory, previousTemporaryFailureCount })`
- persisted `RecoveryAction` creation with `status = RECOMMENDED`
- `RecoveryExecutionService.execute(...)`

The baseline must use:

- the same failed payment scenarios
- the same candidate recovery actions
- the same success/failure label logic
- the same evaluation dataset definition
- the same execution semantics

The baseline cannot be changed to make the comparison easier. It is the production logic to beat.

## 3. Primary metric

The primary business metric is:

```text
recovery_success_rate
```

Definition:

```text
recovery_success_rate = number of payment scenarios successfully recovered / total evaluated payment scenarios
```

More explicitly:

```text
recovery_success_rate = total successful recoveries / total failed-payment evaluation cases
```

This metric measures the proportion of failed payments that ultimately recover successfully under the chosen action strategy.

It is aligned with the actual business goal: recovering failed payments.

This is the primary comparison metric between:

- rule engine recovery success rate
- ML policy recovery success rate

## 4. Secondary metrics

Secondary metrics should be computed only when they can be derived reliably from the evaluation dataset.

### 4.1 Classification-style metrics for action probability quality

These are useful only when the model is evaluated on candidate action probabilities or action labels.

- `precision`: proportion of predicted successful recoveries that were truly successful
- `recall`: proportion of actual successful recoveries that were predicted successfully
- `F1`: harmonic mean of precision and recall

These metrics are acceptable only if the model is evaluated as a binary or multi-class recovery predictor on a valid labeled dataset.

### 4.2 Action-level metrics

- `action_level_recovery_rate`: success rate for the selected action itself
- `retry_success_rate`: success rate when `RETRY` is selected
- `alternate_method_success_rate`: success rate when `ALTERNATE_METHOD` is selected
- `customer_action_success_rate`: success rate when `CUSTOMER_ACTION` is selected
- `escalate_success_rate`: success rate when `ESCALATE` is selected

### 4.3 Aggregate business metrics

- `recovery_rate_by_failure_category`: success rate segmented by `failureCategory`
- `recovery_rate_by_payment_method`: success rate segmented by attempted payment method
- `unnecessary_retry_rate`: frequency of retry actions that do not recover the payment and should have been avoided
- `escalation_rate`: frequency of escalations chosen under the policy
- `alternate_method_success_rate`: success rate of alternate-method recovery actions

### 4.4 Model-quality metrics

Only if the evaluation framework supports them reliably:

- calibration quality
- Brier score
- probability-ranking quality

These are optional and should not replace the primary business metric.

## 5. Dataset split strategy

Because payment history is temporal, the recommended split is chronological rather than random.

### 5.1 Why chronological splitting is preferred

Payment data is time-ordered:

- past attempts inform current behavior
- future events are not available at the time of the decision
- random splits can leak information across time
- future recovery outcomes may appear in the training data for a past case

A chronological split reduces leakage and better reflects the real operational setting.

### 5.2 Recommended strategy

Use a split such as:

- train: earliest period
- validation: middle period
- test: latest period

Example:

```text
Train = oldest 60%
Validation = next 20%
Test = newest 20%
```

This keeps the evaluation realistic and preserves the chronology of payment behavior.

### 5.3 Leakage prevention

The evaluation must prevent leakage by ensuring:

- features are derived only from events that occurred before the candidate decision
- no post-decision recovery outcomes are included in the model input
- no future payment attempts are used for current-case features
- all historical aggregates are computed using only prior data
- test rows are never used to tune model parameters

## 6. Model evaluation methodology

### 6.1 Train / validation / test separation

The evaluation process should follow this pattern:

1. Use historical payment data for training.
2. Tune hyperparameters or selection rules on validation data.
3. Freeze the model and policy.
4. Evaluate on the untouched test set.

This prevents overfitting to the test set.

### 6.2 Class imbalance handling

Recovery outcomes may be imbalanced because successful recoveries may be rarer than failed recoveries, depending on the action class.

The evaluation strategy should consider:

- class distribution by action type
- per-action positive rate
- weighted metrics if necessary
- evaluation within each candidate action class, not just aggregate rates

The design should not assume a balanced dataset.

### 6.3 Action distribution considerations

Because the action space is limited to four action types, the dataset must also be reviewed for:

- how often each action is selected by the baseline rule engine
- how often each action is actually successful
- whether some actions are rare and therefore unstable to evaluate

This matters because a model may perform well on frequent actions but poorly on rare ones.

### 6.4 Reproducibility

Every evaluation must be reproducible with the following metadata:

- dataset version
- feature version
- model version
- evaluation version
- random seed
- evaluation timestamp
- data split boundaries

This ensures the comparison can be replicated later.

## 7. Action-selection evaluation

The model produces probabilities for each candidate action, but the real business value is in the final selected action.

Therefore the evaluation must compare selected actions, not just raw probability outputs.

### 7.1 Evaluation workflow

For each payment scenario in the evaluation set:

1. derive the payment context and available action candidates
2. run Phase 1 rule engine and record the selected action
3. run the ML policy and record the selected action
4. compare the selected action to the actual observed recovery result
5. compute the success rate for each selection path

This yields:

- rule-engine selected action outcome
- ML-selected action outcome

### 7.2 Outcome definition

The outcome for each selected action should follow the Phase 2 target definition:

```text
recovery_success = 1 if the selected action actually succeeded
recovery_success = 0 otherwise
```

This definition must be consistent across baseline and ML evaluation.

### 7.3 Selected-action comparison

For each scenario:

```text
scenario outcome = actual recovery success after selected action
rule_engine_action = selected by Phase 1 rules
ml_action = selected by the ML policy
```

Then compute:

- rule success rate
- ML success rate
- absolute improvement
- relative improvement

## 8. Rule-vs-ML comparison

The final comparison is:

```text
Rule Engine Recovery Rate = successful recoveries under baseline / total failed-payment scenarios
ML Recovery Rate = successful recoveries under ML policy / total failed-payment scenarios
```

Absolute improvement:

```text
Absolute Improvement = ML Recovery Rate - Rule Engine Recovery Rate
```

Relative improvement:

```text
Relative Improvement = (ML Recovery Rate - Rule Engine Recovery Rate) / Rule Engine Recovery Rate
```

Only define relative improvement when the baseline recovery rate is non-zero.

This is the decisive metric for whether Phase 2 adds value.

## 9. Failure analysis

Incorrect intelligent decisions should be analyzed systematically.

Examples of failure categories:

- model selected `RETRY` but `ALTERNATE_METHOD` would have succeeded
- model selected `ALTERNATE_METHOD` but `RETRY` would have succeeded
- model recommended a low-value action with a modest probability but poor outcome
- model predicted a high probability but the action failed
- model avoided a valid action due to a safety constraint or policy filter
- model selected a low-probability action that still recovered successfully

Failure analysis should break down by:

- failure category
- selected action
- probability band
- payment method
- attempt number
- prior temporary-failure count

This helps identify whether the model is systematically wrong in a particular segment or action class.

## 10. Success criteria

The system should only be considered an improvement when the evidence shows a real advantage over the baseline.

The evidence required should include:

1. the ML policy outperforms the rule engine on the held-out test set
2. the improvement is measured using the same evaluation dataset and the same outcome definition
3. the gain is consistent across relevant segments rather than only on one narrow subset
4. the model does not create unsafe or clearly regressive patterns
5. the selected action is better or at least no worse in business-critical scenarios

No arbitrary percentage threshold should be imposed without justification. Instead, the decision should be based on:

- effect size on the primary metric
- consistency across segments
- stability under validation and test periods
- operational safety and policy compliance

It is reasonable to require both a positive absolute improvement and a credible explanation for the underlying gain.

## 11. Reproducibility requirements

Every evaluation run should record:

- dataset version
- feature version
- model version
- evaluation version
- random seed
- evaluation timestamp
- train/validation/test split boundaries
- baseline rule-engine version

This is necessary for:

- auditability
- reproducibility
- future comparison against later models
- debugging regressions

## Summary

The evaluation design is straightforward:

1. treat the current Phase 1 rule engine as the baseline
2. use the same failed-payment scenarios and outcome definition for both baseline and model
3. compare `recovery_success_rate` between the two
4. evaluate by selected action, not by raw probability alone
5. split data chronologically to avoid leakage
6. require evidence that the ML policy meaningfully improves over the baseline before claiming improvement

The purpose is to prove value, not merely to produce a model score.
