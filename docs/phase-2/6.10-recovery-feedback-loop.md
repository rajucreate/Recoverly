# Phase 2 Task 6.10: Recovery Feedback Loop

## 1. Purpose & Scope

The **Recovery Feedback Loop** establishes a closed feedback system connecting model predictions, selected recovery actions, authoritative execution outcomes, structured feedback records, and future training/evaluation datasets.

It bridges the runtime gap between:
```text
Model Prediction (estimated recovery probability)
    ↓
Recovery Decision Policy (selected candidate action)
    ↓
Recovery Execution Service (authoritative payment outcome)
    ↓
Actual Observed Outcome (tri-state: SUCCESS / FAILED / EXECUTED)
    ↓
Structured Feedback Record (schema: 6.10.0)
    ↓
Future Training / Evaluation Dataset (schema: 6.2.1)
```

---

## 2. Core Architectural Invariants & Isolation

### 2.1 The Critical Semantic Invariant
$$\text{predicted\_recovery\_probability} \neq \text{actual\_recovery\_success}$$

- **Model Prediction:** An estimated probability ($0.0 \le p \le 1.0$) generated prior to recovery execution by the frozen Phase 2 model artifact.
- **Actual Observed Outcome:** Derived **only** after execution completes via `RecoveryExecutionService` and the payment provider.
- **Strict Non-Derivation:** `actual_recovery_success` is **never** derived, inferred, or calculated from `predicted_recovery_probability`.

### 2.2 Authoritative Tri-State Outcome Semantics
Payment attempt and non-attempt actions produce distinct authoritative outcomes:
- **`SUCCESS`** $\rightarrow$ `actual_recovery_success = true` (payment successfully recovered)
- **`FAILED`** $\rightarrow$ `actual_recovery_success = false` (payment recovery attempt failed)
- **`EXECUTED`** $\rightarrow$ `actual_recovery_success = null` (non-payment action successfully completed; payment recovery is unobserved / pending out-of-band resolution, never defaulted to failure)

### 2.3 Operational Isolation & Runtime Integration Boundaries
- **Integration Boundary:** Feedback recording is integrated inside `TransactionController.executeRecovery` after `RecoveryExecutionService.execute()` returns its authoritative result.
- **Single Execution Path:** `RecoveryExecutionService` remains the sole, authoritative recovery execution path and is **completely unmodified**.
- **Observational Safety:** Any feedback recording failure is caught safely and never causes an already-completed recovery execution request to fail.
- **Zero Schema Migrations:** `schema.prisma` is **completely unmodified**.

## 3. Feedback Record Schema Specification (`version: 6.10.0`)

```typescript
interface FeedbackRecord {
  feedback_id: string;                     // Unique feedback ID ('feedback_' prefix)
  feedback_schema_version: string;         // '6.10.0'
  feedback_timestamp: string;              // ISO 8601 UTC timestamp of feedback capture
  correlation: {
    transaction_id: string;                // ID of transaction
    trigger_attempt_id: string;            // ID of failed attempt triggering recovery
    recovery_action_id: string | null;     // ID of the recovery action
    execution_attempt_id: string | null;   // ID of new attempt created during recovery (null if non-payment action)
  };
  decision: {
    selected_action: string;               // 'RETRY' | 'ALTERNATE_METHOD' | 'CUSTOMER_ACTION' | 'ESCALATE'
    decision_source: 'ML' | 'RULE';        // Source mechanism
    predicted_recovery_probability: number | null; // Model probability (null if RULE)
    model_version: string | null;          // Model version ID (null if RULE)
    decision_reason: string;               // Justification text
    fallback: {
      is_fallback: boolean;                // True if resolved via Phase 1 rules
      fallback_reason: string | null;      // Reason for fallback
      fallback_error: string | null;       // Underlying error message if applicable
    };
  };
  context: {
    transaction_amount: number | null;     // Transaction amount
    currency: string | null;               // Currency code (e.g., 'INR')
    payment_method_attempted: string | null;// Payment method (UPI, CARD, NET_BANKING)
    failure_category: string | null;       // Category of failure
    has_failure_reason: boolean;           // Whether failure reason was present
    failure_reason_text: string | null;    // Description of failure
    attempt_number: number;                // Attempt counter
    prior_failed_attempt_count: number;    // Count of failed attempts
    prior_temporary_failure_count: number; // Count of temporary failures
    prior_payment_method_history: string;  // Serialized history
  };
  execution: {
    execution_outcome: 'SUCCESS' | 'FAILED' | 'EXECUTED'; // Authoritative outcome
    actual_recovery_success: boolean | null; // true for SUCCESS, false for FAILED, null for EXECUTED
    outcome_timestamp: string;             // ISO 8601 UTC timestamp of execution
  };
  versions: {
    model_version: string | null;
    feature_schema_version: string;        // '6.3.1'
    feature_pipeline_version: string;      // '1.0.0'
    policy_version: string;                // '6.7.0'
    audit_schema_version: string;          // '6.7.0'
    feedback_schema_version: string;       // '6.10.0'
  };
}
```

## 4. ML vs RULE Representation in Feedback

| Property | ML Decision Feedback | RULE Fallback Feedback |
| :--- | :--- | :--- |
| `decision.decision_source` | `'ML'` | `'RULE'` |
| `decision.predicted_recovery_probability` | Numeric in `[0.0, 1.0]` | `null` |
| `decision.model_version` | `'phase2-interaction-logistic-v1'` | `null` |
| `decision.fallback.is_fallback` | `false` | `true` |
| `execution.actual_recovery_success` | `true` / `false` / `null` | `true` / `false` / `null` |
| `execution.execution_outcome` | `'SUCCESS'`, `'FAILED'`, or `'EXECUTED'` | `'SUCCESS'`, `'FAILED'`, or `'EXECUTED'` |

## 5. Dataset Transformation for Retraining / Evaluation

Feedback records can be exported directly into rows matching the Phase 2 dataset schema (`schema_version: 6.2.1`):

```javascript
import { feedbackRecordToDatasetRow } from './recovery-feedback-service.js';

const datasetRow = feedbackRecordToDatasetRow(feedbackRecord);
```

### Column Mapping:
- `record_id`: Unique row ID (`fb_row_...`)
- `decision_id`: `feedbackRecord.feedback_id`
- `decision_timestamp`: `feedbackRecord.feedback_timestamp`
- `transaction_id`: `feedbackRecord.correlation.transaction_id`
- `attempt_id`: `feedbackRecord.correlation.trigger_attempt_id`
- `transaction_amount`: `Number(feedbackRecord.context.transaction_amount)`
- `currency`: `feedbackRecord.context.currency`
- `payment_method`: `feedbackRecord.context.payment_method_attempted`
- `failure_category`: `feedbackRecord.context.failure_category`
- `failure_reason_present`: `Boolean(feedbackRecord.context.has_failure_reason)`
- `failure_reason_text`: `feedbackRecord.context.failure_reason_text`
- `attempt_number`: `Number(feedbackRecord.context.attempt_number)`
- `prior_failed_attempt_count`: `Number(feedbackRecord.context.prior_failed_attempt_count)`
- `prior_temporary_failure_count`: `Number(feedbackRecord.context.prior_temporary_failure_count)`
- `prior_payment_method_history`: `feedbackRecord.context.prior_payment_method_history`
- `candidate_action`: `feedbackRecord.decision.selected_action`
- `selected_action`: `feedbackRecord.decision.selected_action`
- `action_executed`: `true`
- `recovery_success`: `feedbackRecord.execution.actual_recovery_success === true ? 1 : 0`
- `recovery_outcome`: `feedbackRecord.execution.execution_outcome === 'SUCCESS' ? 'SUCCESS' : 'FAILED'`
- `outcome_timestamp`: `feedbackRecord.execution.outcome_timestamp`
- `dataset_version`: `'v1'`
- `schema_version`: `'6.2.1'`

## 6. Duplicate Prevention & Deterministic Idempotency

`RecoveryFeedbackService` generates deterministic deduplication keys based on:
$$\text{key} = \text{transaction\_id} : \text{recovery\_action\_id} : \text{execution\_outcome}$$

- If an execution outcome for a given recovery action is recorded more than once, the service deterministically returns the existing record without appending duplicates.
- An in-memory ring buffer (default capacity 1,000 records) manages storage with FIFO eviction.

---

## 7. Storage Limitations & Phase 2 Lifecycle Scope

- **In-Memory Buffer Management:** In Phase 2, `RecoveryDecisionAuditService` and `RecoveryFeedbackService` operate using in-memory ring buffers with FIFO eviction (default buffer size: 1,000 records).
- **No Durable Database Persistence in Phase 2:** Per architectural constraints, `schema.prisma` is untouched and no database tables are created for feedback storage in Phase 2.
- **Service Lifetime:** Audit and feedback records reside in process memory for the lifetime of the application instance. Long-term durable persistence, partitioned data lakes, and continuous automated training pipelines remain explicitly scoped for future architectural phases.
