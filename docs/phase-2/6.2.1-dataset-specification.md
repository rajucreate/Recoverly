# Phase 2: Historical Payment Dataset Schema & Generation Specification

## 1. Dataset objective

This document defines the historical recovery dataset specification for the Phase 2 intelligent recovery model.

The dataset is designed to support learning:

```text
P(recovery_success | payment_context, candidate_action)
```

The dataset must support:

1. training the model
2. evaluating the model
3. comparing ML performance against the Phase 1 rule engine
4. analyzing recovery performance by failure mode, action, and payment method

The dataset is defined at the event level, not as a direct copy of the live transactional database. Each row represents a recovery decision event with pre-decision context, a candidate action, and an observed outcome when the action was actually executed.

## 2. Canonical record structure

Each canonical record is one historical recovery decision row.

The row consists of three groups:

1. pre-decision features
2. decision metadata
3. post-execution outcome data

### 2.1 Required fields

```text
record_id
decision_timestamp
transaction_id
attempt_id
transaction_amount
currency
payment_method
failure_category
failure_reason_present
failure_reason_text
attempt_number
prior_failed_attempt_count
prior_temporary_failure_count
prior_payment_method_history
candidate_action
selected_action
action_executed
recovery_success
recovery_outcome
outcome_timestamp
dataset_version
schema_version
```

### 2.2 Field definitions

| Field | Type | Meaning | Timing |
|---|---|---|---|
| `record_id` | string | unique row identifier for this decision candidate | generated at record creation |
| `decision_timestamp` | datetime | timestamp when the recovery decision is evaluated | before decision |
| `transaction_id` | string | transaction being evaluated | before decision |
| `attempt_id` | string | failed payment attempt that triggered the decision | before decision |
| `transaction_amount` | numeric | amount from `Transaction.amount` | before decision |
| `currency` | enum | `Transaction.currency` | before decision |
| `payment_method` | enum | attempted payment method from `PaymentAttempt.paymentMethod` | before decision |
| `failure_category` | enum | `PaymentAttempt.failureCategory` | before decision |
| `failure_reason_present` | boolean | whether `failureReason` exists | before decision |
| `failure_reason_text` | string/null | raw reason text if available | before decision |
| `attempt_number` | integer | `PaymentAttempt.attemptNumber` | before decision |
| `prior_failed_attempt_count` | integer | count of prior failed attempts before this event | before decision |
| `prior_temporary_failure_count` | integer | count of prior temporary failures before this event | before decision |
| `prior_payment_method_history` | structured | previous method usage pattern | before decision |
| `candidate_action` | enum | action under evaluation | decision-time |
| `selected_action` | enum | actual action chosen in the real event or policy decision | decision-time |
| `action_executed` | boolean | whether the candidate action was actually executed in history | after decision |
| `recovery_success` | integer {0,1} | target label | after execution |
| `recovery_outcome` | enum/string | observed action outcome, e.g. `SUCCESS`, `FAILED` | after execution |
| `outcome_timestamp` | datetime | time the action outcome was observed | after execution |
| `dataset_version` | string | dataset version | metadata |
| `schema_version` | string | schema specification version | metadata |

## 3. Feature / decision / outcome separation

The dataset must clearly separate the information used before the decision from the post-decision outcome.

### 3.1 Pre-decision features

These fields are valid model inputs:

- `transaction_amount`
- `currency`
- `payment_method`
- `failure_category`
- `failure_reason_present`
- `failure_reason_text` only if text is explicitly used in a controlled text pipeline
- `attempt_number`
- `prior_failed_attempt_count`
- `prior_temporary_failure_count`
- `prior_payment_method_history`
- `candidate_action`

These are all available before the recovery decision is made.

### 3.2 Decision metadata

These fields describe the candidate and selected action:

- `candidate_action`
- `selected_action`
- `decision_timestamp`
- `record_id`

These are not outcome data and must not be used as post-decision labels.

### 3.3 Outcome / label data

These fields are available only after the recovery action is executed:

- `action_executed`
- `recovery_success`
- `recovery_outcome`
- `outcome_timestamp`

These fields are the label source and must never appear in the pre-decision feature set.

## 4. Candidate-action representation

The model scores one candidate action at a time, so the historical dataset should represent candidate-action rows explicitly.

The canonical pattern is:

```text
payment_decision_123 + RETRY
payment_decision_123 + ALTERNATE_METHOD
payment_decision_123 + CUSTOMER_ACTION
payment_decision_123 + ESCALATE
```

For each action row:

- `candidate_action` identifies the action under evaluation
- `selected_action` captures which action was actually chosen in the historical record
- `action_executed` tells whether that candidate was actually executed
- `recovery_success` is populated only for the executed candidate, or for an observed counterfactual if the data pipeline intentionally models it

### 4.1 Important distinction

Not every candidate action is necessarily executed in the real process.

Therefore the dataset must distinguish:

- candidate rows produced for model scoring
- observed execution rows from real history

Recommended handling:

- if the action was actually executed, set `action_executed = true`, `selected_action = same as candidate_action`, and populate `recovery_success`
- if the action was not executed, set `action_executed = false` and set `recovery_success = null` for that row
- such rows are valid for model scoring experiments only if they are explicitly treated as unobserved candidate actions, not as label-bearing examples

This avoids confusing a candidate-action score with an observed outcome.

## 5. Target definition

The target is:

```text
recovery_success
```

with exact semantics:

```text
1 = the candidate/selected recovery action successfully recovered the payment
0 = it did not recover the payment
```

This is the same target defined in Phase 2 6.1.1.

For historical rows where the action was not actually executed:

```text
recovery_success = null
```

and the row must be excluded from supervised training for action-success modeling.

## 6. Synthetic generation methodology

This task does not generate the final dataset, but it defines the generation rules for a realistic synthetic historical dataset.

### 6.1 Generation principles

The synthetic dataset must:

- be realistic, not uniform random noise
- contain meaningful relationships between context and outcome
- contain signal and noise
- allow the Phase 1 rule engine and the future ML policy to be compared under common conditions
- preserve temporal ordering
- avoid perfect determinism

### 6.2 Transaction amounts

Generate amounts with realistic skew and realistic distributions:

- small and medium transactions dominate
- larger transactions exist but less frequently
- values should be positive and bounded by the product domain

Recommended style:

- log-normal or skewed distribution with truncation to realistic business amounts
- avoid uniform random values over a wide range

### 6.3 Currencies

Represent realistic currency usage:

- INR as the dominant currency for the sample
- optional secondary currencies with lower frequency
- keep the currency field categorical and use realistic proportions

### 6.4 Payment methods

Generate payment method distribution by scenario:

- UPI frequent
- CARD common
- NET_BANKING less common

The method should influence outcome likelihood, especially for alternate-method recovery scenarios.

### 6.5 Failure categories

Generate failure categories using realistic proportions:

- `TEMPORARY_FAILURE`: common for retryable failures
- `PAYMENT_METHOD_FAILURE`: common when a method-specific issue occurs
- `CUSTOMER_ACTION_REQUIRED`: lower but non-zero frequency
- `UNKNOWN_FAILURE`: moderate frequency

These categories should affect both recommended actions and outcomes.

### 6.6 Failure reasons

Generate reason text or indicator with dependency on failure category:

- temporary failures should have transient texts such as timeout, connectivity issue, gateway response issue
- payment-method failures should reference card decline, bank rejection, or method-specific error
- customer-action failures should reference authentication, OTP, KYC, consent, or action-required conditions
- unknown failures should have generic or ambiguous text

Keep the raw text realistic but not too deterministic.

### 6.7 Attempt counts and retry behavior

Generate historical payment attempts with realistic retry patterns:

- most transactions fail once or twice before resolution
- repeated temporary failures should become less likely to succeed
- later attempts may still succeed if the failure is transient and the issue clears
- repeated retries beyond the Phase 1 retry policy should be less effective and more likely to fail

This reflects actual payment retry behavior without making the target trivial.

### 6.8 Historical behavior patterns

Historical context should influence recovery success:

- a temporary failure on a low-value payment may be more retryable than on a high-risk payment scenario
- alternate method may succeed more often when the original method had a method-specific failure
- repeated retries should gradually reduce success probability
- unknown or customer-action failures are less likely to respond to simple retry behavior

### 6.9 Recovery actions

Generate candidate actions with realistic business logic:

- `RETRY` is common for temporary failures
- `ALTERNATE_METHOD` is common for payment method failures
- `CUSTOMER_ACTION` is common for customer action requirements
- `ESCALATE` is common for unknown or exhausted retry paths

The action distribution should reflect the existing rule engine but should still allow noisy or overlapping outcomes.

### 6.10 Recovery outcomes

Outcomes must depend on both context and chosen action:

- retry success depends on failure category and retry depth
- alternate-method success depends on method mismatch and method-specific failure type
- customer action success depends on whether the customer action is actually completed and the scenario is valid
- escalate success depends on operational resolution and may be rare or slow

The outcome model must include signal and noise so that the target is not perfectly predicted by the Phase 1 rule engine alone.

## 7. Dependency and relationship rules

The dataset generation rules must preserve realistic dependencies.

### 7.1 Required relationships

- temporary failures should differ from payment-method failures in recovery success patterns
- retry success should decline with repeated attempts
- alternate method should be more successful on `PAYMENT_METHOD_FAILURE` than on `TEMPORARY_FAILURE`
- customer action requirements should favor `CUSTOMER_ACTION`
- unknown failures should be harder to recover with a simple retry
- the selected action and the payment context should jointly determine outcome

### 7.2 Rules to avoid

- avoid generating completely independent random features with no context coupling
- avoid making the rule engine redundant by generating perfect deterministic outcomes from a single categorical field
- avoid making the target trivially predictable by using outcome features directly

## 8. Noise strategy

The synthetic dataset should contain noise so the model learns realistic patterns rather than memorizing deterministic rules.

Recommended noise profile:

- moderate stochastic variation in success outcome for each action
- overlapping success rates among actions in some scenarios
- inconsistent but realistic partial recovery success for temporary or unknown failures
- random variation in failure reason text while preserving category semantics

The noise should be enough to make the task non-trivial but not enough to destroy the signal.

## 9. Temporal strategy

The dataset should be generated over a realistic historical time range.

Recommended setup:

- span 6 to 12 months of payment activity
- timestamps should be ordered and realistic, not all identical
- distribute events across time with bursts, weekday/weekend variation, and retry timing
- preserve causal ordering for train/validation/test splitting

This ensures the dataset supports the chronological evaluation split defined in 6.1.5.

## 10. Class and action distribution strategy

The dataset should resemble realistic business behavior, not artificially balanced data.

Recommended distributions:

- payment methods: UPI > CARD > NET_BANKING
- failure categories: `TEMPORARY_FAILURE` largest, then `PAYMENT_METHOD_FAILURE`, then `UNKNOWN_FAILURE`, then `CUSTOMER_ACTION_REQUIRED`
- action types: reflect true recovery decisions, with `RETRY` and `ALTERNATE_METHOD` more common than `CUSTOMER_ACTION` or `ESCALATE`
- successful recoveries: less common than failed recoveries overall; some actions will be far rarer than others

Do not oversample or undersample aggressively in the synthetic dataset if the goal is realistic evaluation.

## 11. Leakage prevention

The dataset schema must enforce strict temporal and causal integrity.

### 11.1 Forbidden leakage sources

The following must not appear in the model feature columns:

- post-decision `RecoveryAction.status`
- outcome-derived `recovery_success` fields before label assignment
- final transaction status after action execution
- the next payment attempt created after the action
- future payment attempts or future recovery outcomes
- any feature computed from events after the observed decision timestamp

### 11.2 Causal ordering

Every feature must be available at or before `decision_timestamp`.

All outcome columns must be observed after or at the point of execution and must be explicitly labeled as post-decision information.

## 12. Dataset size recommendation

For a first realistic ML experiment, the dataset should be large enough to represent the action space and failure patterns without being impractical.

Recommended initial dataset size:

```text
10,000 to 30,000 historical decision rows
```

This is enough for:

- initial training and validation
- action-type coverage
- baseline comparison
- failure-category analysis
- basic model experimentation

A much larger dataset is not required for the first design stage.

## 13. Versioning

The dataset must be versioned for reproducibility.

Required fields:

- `dataset_version`
- `schema_version`
- `generator_version`
- `random_seed`
- `generation_timestamp`

Recommended metadata:

- feature schema version
- action schema version
- evaluation schema version

## 14. Reproducibility

The dataset must be reproducible.

Given:

- the same seed
- same generator version
- same generation config
- same schema version

the same dataset should be generated.

This is essential for:

- reproducible experiments
- comparing model iterations
- debugging data drift
- reproducing evaluation results

## 15. Data-quality validation requirements

Before using the dataset for training or evaluation, validate:

1. no missing required identifier fields
2. all timestamps are ordered correctly
3. all categorical enums are valid
4. `recovery_success` is only present for executed or observed actions
5. no post-decision features are included in the pre-decision feature set
6. `candidate_action` is one of the supported actions
7. `selected_action` and `candidate_action` align appropriately
8. outcomes are consistent with action execution semantics
9. dataset version metadata is present
10. chronological split boundaries are valid

## Summary

The historical payment dataset should be modeled as a decision-event table with pre-decision features, candidate-action metadata, and post-decision outcome fields.

The canonical row is:

```text
(payment context before decision, candidate action, observed success/failure after execution)
```

This design matches the actual Recoverly flow, preserves causal integrity, and provides the structure needed for both model training and rule-vs-ML evaluation without modifying Phase 1 behavior.
