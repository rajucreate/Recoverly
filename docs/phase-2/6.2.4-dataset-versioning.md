# Phase 2: Dataset Versioning & Reproducibility

## 1. Versioning convention

The first offline dataset uses lightweight fixed identifiers:

- Dataset: `v1`, filename `recovery_dataset_v1.csv`
- Schema: `6.2.1`, matching the approved dataset specification
- Generator: `1.0.0`
- Source specification: `6.2.1`

The dataset version changes when the dataset contract or generated dataset meaning changes. The generator version changes when generation behavior changes. The schema version changes when the row contract changes.

## 2. Metadata contract

The canonical metadata file is `data/phase-2/recovery_dataset_v1.metadata.json`.

It contains:

- `dataset_version`
- `schema_version`
- `generator_version`
- `random_seed`
- `row_count`
- `generated_at`
- `source_specification_version`
- `dataset_file_name`
- `dataset_sha256`
- generation configuration, including seed, row count, and start timestamp

`generator-run-summary.json` is not retained because it duplicated the canonical metadata and output paths.

## 3. Reproducibility rules

The CSV content is deterministic for the same:

- generator version
- configuration
- random seed
- schema/source specification

`generated_at` records when an artifact was written and is metadata only. It is not included in the CSV, so it does not affect the dataset content hash.

## 4. Checksum strategy

The generator computes SHA-256 over the exact UTF-8 bytes written to the CSV, including its header and final newline. The hexadecimal digest is stored as `dataset_sha256` in the metadata file.

The validator recomputes the hash from the dataset file and fails if the metadata digest differs. This detects edits, truncation, formatting changes, or metadata/file mismatches.

## 5. Dataset identity

A dataset artifact is identified by the combination of:

```text
(dataset_version, schema_version, generator_version, random_seed, configuration, dataset_sha256)
```

The checksum is the final content identity; the other fields explain how that content was produced.

## 6. Validation behavior

Run:

```bash
node src/intelligence/validate-recovery-dataset.js
```

Validation checks that:

- all required metadata fields exist
- metadata row count matches the CSV
- metadata file name matches the dataset file
- source specification version is supported
- metadata SHA-256 matches the exact CSV content
- existing structural, temporal, distribution, causal, candidate-action, and leakage checks still pass

A critical failure sets a non-zero process exit code.

## 7. Reproduce the current dataset

From `backend/`, run:

```bash
node src/intelligence/generate-recovery-dataset.js --seed 42 --row-count 6000
```

This regenerates `data/phase-2/recovery_dataset_v1.csv` and its canonical metadata. The resulting CSV content should have the same SHA-256 as the checked-in metadata when the generator version and configuration are unchanged.

No ML model is trained, and no Phase 1 runtime behavior is involved.
