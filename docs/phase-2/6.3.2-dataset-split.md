# Phase 2: Chronological Train/Validation/Test Split

## 1. Split strategy

The split follows the chronological strategy in 6.1.5:

- earliest 60%: training
- following 20%: validation
- latest 20%: test

Rows are ordered by the original raw dataset `decision_timestamp`. No random shuffle or seed-dependent assignment is used.

## 2. Temporal boundaries

The generated metadata in `data/phase-2/splits/splits.metadata.json` records the first and last timestamp for each partition. The validator requires:

```text
max(train decision_timestamp) < min(validation decision_timestamp)
max(validation decision_timestamp) < min(test decision_timestamp)
```

## 3. Split proportions

For `N` rows:

- train receives `floor(N * 0.60)` rows
- validation receives `floor(N * 0.20)` rows
- test receives the remaining rows

For the current 6,000-row dataset this produces 3,600 training rows, 1,200 validation rows, and 1,200 test rows.

## 4. Feature/target separation

Each split CSV contains the 19 model-ready feature columns from 6.3.1 plus `recovery_success` as the final target column. The target is not part of the feature schema or feature matrix.

The split files exclude transaction IDs, decision IDs, attempt IDs, timestamps, executed-action fields, and recovery outcome fields.

## 5. Distribution characteristics

`split_metadata.json` records per-split counts and percentages for:

- `recovery_success`
- `candidate_action`
- `failure_category`
- `payment_method`

The splitter does not rebalance or fabricate missing categories.

## 6. Leakage prevention

Raw rows are used for timestamp ordering, target extraction, and audit only. Feature rows are paired by their existing source-row alignment and are never augmented with identifiers. Split validation rejects forbidden columns, overlap, duplicate decision/action pairs, and target absence.

## 7. Reproducibility

The same raw dataset and feature artifact produce identical split rows for the same split version and proportions. `random_seed` is recorded as `null` because chronological assignment does not use randomness.

## 8. Validation

The splitter validates:

- raw and feature row counts match
- timestamps are valid and chronological within partitions
- temporal boundaries do not overlap
- all rows reconcile exactly once
- target values are `0` or `1`
- feature ordering is deterministic
- forbidden model-input fields are absent

## 9. How to regenerate the splits

From `backend/`:

```bash
node src/intelligence/generate-recovery-splits.js
```

Generated artifacts:

- `data/phase-2/splits/train.csv`
- `data/phase-2/splits/validation.csv`
- `data/phase-2/splits/test.csv`
- `data/phase-2/splits/splits.metadata.json`

This task does not train a model and does not change the raw dataset or Phase 1 runtime behavior.
