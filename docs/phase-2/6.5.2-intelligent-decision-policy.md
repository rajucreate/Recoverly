# Phase 2: Intelligent Recovery Decision Policy

## 1. Architecture

The policy is a standalone advisory layer between action-specific prediction and the existing Phase 1 recovery flow:

```text
Failed payment context
  -> RecoveryPredictionService.predictAll()
  -> RecoveryDecisionPolicy
  -> selected action result
  -> existing Phase 1 persistence and execution flow
```

The policy is implemented in `backend/src/intelligence/recovery-decision-policy.js`.

- `RecoveryPredictionService` estimates recovery probabilities.
- `RecoveryDecisionPolicy` validates, filters, ranks, and selects a candidate.
- `RecoveryDecisionEngine` supplies the deterministic fallback.
- `RecoveryExecutionService` remains the only execution component.

The policy does not persist actions, mutate transaction state, call providers, or execute recovery actions.

## 2. Prediction to policy flow

`RecoveryDecisionPolicy.decide(context)` passes the decision-time context to `predictAll()`. The prediction service returns one prediction for each supported action in this order:

```text
RETRY -> ALTERNATE_METHOD -> CUSTOMER_ACTION -> ESCALATE
```

The policy validates that all four actions are present exactly once, every probability is finite and in `[0, 1]`, and every prediction has consistent non-empty model metadata. Invalid output is rejected as a whole.

## 3. Candidate filtering and safety

Candidates are removed when the context shows that:

- the transaction is not in `FAILED` state;
- the action has already been executed;
- `RETRY` is not for a temporary failure;
- the temporary-failure retry limit from `RecoveryDecisionEngine` has been reached;
- an alternate method is known to be the same as the failed method; or
- no different method is available when available methods are supplied.

The policy only filters candidates. Phase 1 still validates transaction state, action ownership, action status, payment method, duplicate execution, provider outcome, and database transitions during the normal runtime flow.

## 4. Ranking and selection

Remaining candidates are ranked by descending `recovery_probability`. Equal probabilities are resolved by the fixed action order above. The highest-probability safe candidate is returned with `decision_source: "ML"`.

## 5. Fallback behavior

The policy delegates to `RecoveryDecisionEngine.decide()` when:

- the prediction service throws;
- prediction structure or metadata is invalid;
- a probability is outside `[0, 1]`; or
- no candidate is safe for the supplied context.

Fallback results have `decision_source: "RULE"`, null probability and model version, the original candidate predictions when valid, and a stable `fallback_reason` constant:

- `MODEL_UNAVAILABLE`
- `INVALID_PREDICTION`
- `NO_SAFE_CANDIDATE`

The rule result remains authoritative for fallback behavior and is not modified by this policy.

## 6. Result contract

An ML result has this shape:

```json
{
  "selected_action": "RETRY",
  "decision_source": "ML",
  "recovery_probability": 0.82,
  "model_version": "phase2-interaction-logistic-v1",
  "reason": "ML selected RETRY as the highest-probability safe recovery action.",
  "candidate_predictions": []
}
```

A rule fallback has this shape:

```json
{
  "selected_action": "RETRY",
  "decision_source": "RULE",
  "recovery_probability": null,
  "model_version": null,
  "reason": "The failure is classified as temporary, so retrying the payment is recommended.",
  "candidate_predictions": [],
  "fallback_reason": "MODEL_UNAVAILABLE"
}
```

The policy does not invent or evaluate a confidence score.

## 7. Responsibility boundaries

The selected action is a recommendation result only. A later integration may pass it into the existing Phase 1 action-creation path, which continues to create a `RECOMMENDED` action. `RecoveryExecutionService` remains responsible for executable action state, transaction validation, payment-provider calls, recovery attempts, and final transaction status.

## 8. Confidence thresholds

Confidence thresholds are intentionally deferred to 6.7. Recovery probability and confidence represent different concepts. Introducing a threshold here would add an unapproved policy gate before the confidence and uncertainty design is defined. The current policy therefore uses only validated action probabilities and deterministic safety constraints.
