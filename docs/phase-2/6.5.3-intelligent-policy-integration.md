# Phase 2: Intelligent Policy Integration into Transaction Recovery

## 1. Previous Phase 1 flow

The Phase 1 recovery flow in `TransactionService.createPaymentAttempt`:

```text
Payment attempt created
  → Transaction status updated to FAILED
  → RecoveryDecisionEngine.decide({ failureCategory, previousTemporaryFailureCount })
  → RecoveryAction created with actionType + reason, status = RECOMMENDED
  → RecoveryExecutionService remains unchanged for execution
```

The rule engine directly mapped failure categories to recovery actions deterministically.

## 2. New integrated flow

The Phase 2 recovery flow adds an advisory ML layer:

```text
Payment attempt created
  → Transaction status updated to FAILED
  → Build prediction context from transaction + attempt data
  → Intelligent Recovery Decision Policy:
      ├─ RecoveryPredictionService.predictAll(context)
      │   └─ Returns action-specific recovery probabilities
      │
      └─ If ML succeeds:
         └─ Rank and filter candidates
         └─ Select highest-probability safe action
      
      ├─ If ML fails:
         └─ Fall back to RecoveryDecisionEngine
      
  → RecoveryAction created with selected actionType + reason, status = RECOMMENDED
  → RecoveryExecutionService remains unchanged for execution
```

## 3. Exact integration point

File: `backend/src/services/transaction-service.js`

Location: `TransactionService.createPaymentAttempt`, around line 50-61.

**Before:**
```javascript
const decision = this.recoveryDecisionEngine.decide({
  failureCategory: data.failureCategory,
  previousTemporaryFailureCount: transaction.paymentAttempts.length
});
recoveryAction = await new RecoveryActionRepository(repository.prisma).create({
  transactionId,
  attemptId: attempt.id,
  actionType: decision.actionType,
  reason: decision.reason,
  status: 'RECOMMENDED'
});
```

**After:**
```javascript
const predictionContext = {
  transaction_amount: transaction.amount,
  currency: transaction.currency,
  payment_method_attempted: data.paymentMethod,
  failure_category: data.failureCategory,
  has_failure_reason: !!data.failureReason,
  attempt_number: transaction._count.paymentAttempts + 1,
  prior_failed_attempt_count: transaction.failedAttempts?.length ?? 0,
  prior_temporary_failure_count: transaction.paymentAttempts?.length ?? 0,
  transaction_status: 'FAILED'
};

const decision = this.decisionPolicy.decide(predictionContext);
recoveryAction = await new RecoveryActionRepository(repository.prisma).create({
  transactionId,
  attemptId: attempt.id,
  actionType: decision.selected_action,
  reason: decision.reason,
  status: 'RECOMMENDED'
});
```

## 4. ML decision path

When the policy selects an ML recommendation:

1. `RecoveryPredictionService.predictAll(context)` returns four action-specific probabilities.
2. Policy validates all predictions are present, valid, and consistent.
3. Unsafe candidates are filtered (violated retry limits, alternate-method conflicts, duplicate executions, invalid transaction state).
4. Remaining candidates are ranked by descending probability, with deterministic tie-breaking.
5. Highest-probability candidate is selected.
6. Decision result includes:
   - `selected_action`: the chosen recovery action
   - `decision_source: 'ML'`
   - `recovery_probability`: the model's estimate
   - `model_version`: identifies the frozen model
   - `reason`: explains the ML selection
   - `candidate_predictions`: full ranked list

## 5. Rule fallback path

The policy falls back to `RecoveryDecisionEngine.decide()` when:

- Prediction service throws an error (model not found, schema mismatch, etc.)
- Prediction structure is invalid (missing actions, malformed probabilities, inconsistent versions)
- A probability is outside `[0, 1]`
- No candidate is safe for the payment context

Fallback result:
- `selected_action`: the rule-based action
- `decision_source: 'RULE'`
- `recovery_probability: null`
- `model_version: null`
- `reason`: the rule engine's reasoning
- `fallback_reason`: enum indicating why ML was skipped
- Optional `fallback_error`: error message if caused by an exception

## 6. Persistence behavior

Both ML and rule decisions result in the same `RecoveryAction` schema:

- `transactionId`: the transaction being recovered
- `attemptId`: the failed payment attempt
- `actionType`: the selected recovery action (RETRY | ALTERNATE_METHOD | CUSTOMER_ACTION | ESCALATE)
- `reason`: explanation from policy or rule engine
- `status`: RECOMMENDED (unchanged)

**Metadata not persisted:**

ML decision metadata (`decision_source`, `recovery_probability`, `model_version`, `candidate_predictions`) are not persisted to the database because:

1. The `RecoveryAction` schema does not include fields for these.
2. A Prisma schema migration is not performed for Phase 2 integration.
3. Metadata is retained in the decision result for logging/observability but not stored.

Future phases may introduce a separate analytics or audit table if ML decision tracking becomes necessary.

## 7. Execution boundary

The integration does not change or bypass the existing `RecoveryExecutionService`:

- The execution service remains the **only** component that transitions action state (RECOMMENDED → EXECUTED → SUCCESS/FAILED).
- It continues to validate the transaction is FAILED, the action belongs to the transaction, and the action is in RECOMMENDED state.
- It continues to call the payment provider and update transaction status.
- The recommended action from the policy or rule engine is passed through the existing execution flow unchanged.

## 8. Safety guarantees

All existing Phase 1 safety rules remain enforced:

### Validation
- Transaction must be in FAILED state before recovery decision.
- Action must belong to the transaction.
- Action status transitions follow Phase 1 state machine.

### Retry constraints
- RETRY is only valid for TEMPORARY_FAILURE failures.
- Retry limit (default 2) from `RecoveryDecisionEngine` is enforced.
- Both ML and rule paths respect this limit.

### Alternate-method constraints
- ALTERNATE_METHOD requires a different payment method than the failed attempt.
- Enforced by policy's `hasSafeAlternateMethod()` check.
- Rule engine also validates this during execution.

### Duplicate execution protection
- Each attempt has a unique `RecoveryAction`.
- Attempted actions are filtered from the policy's candidate set.
- Execution service prevents re-executing actions in non-RECOMMENDED state.

### Transaction state transitions
- FAILED → SUCCESS only through recovery execution.
- FAILED → RECOVERED is the existing terminal state for successfully recovered transactions.
- No ML decision bypasses these transitions.

## 9. Metadata limitations

Recovery probability, model version, and decision source are advisory information at the decision layer only. They are not persisted because:

- No schema migration was performed.
- The focus of 6.5.3 is connecting the policy to the existing flow, not changing the data model.
- Future phases (6.7, 6.8, 6.11) may introduce proper audit/analytics tables.

For now:

- These metadata fields are available in the decision result.
- They can be logged or used for observability/monitoring.
- They are not available in `RecoveryAction` queries without a schema change.

## 10. Error handling

### Prediction service failure
If `RecoveryPredictionService` throws (e.g., model file missing, schema mismatch):
- Policy catches the error.
- Falls back to `RecoveryDecisionEngine.decide()`.
- Returns fallback result with `fallback_reason: 'MODEL_UNAVAILABLE'`.
- Transaction flow continues normally.

### Invalid prediction output
If predictions are malformed (missing actions, invalid probabilities, inconsistent versions):
- Policy validation rejects the entire batch.
- Falls back to rule engine.
- Returns fallback result with `fallback_reason: 'INVALID_PREDICTION'`.

### No safe ML candidate
If all ML candidates are unsafe (e.g., retry limit reached, no alternate methods available):
- Policy filters to zero candidates.
- Falls back to rule engine.
- Returns fallback result with `fallback_reason: 'NO_SAFE_CANDIDATE'`.

### Phase 1 fallback failure
If rule engine throws (unsupported failure category):
- This is the same behavior as Phase 1.
- The error propagates as a transaction failure.
- No new error paths are introduced.

## 12. Prisma schema verification

**Schema changes: NONE**

The integration uses only existing `RecoveryAction` fields:
- `id`, `transactionId`, `attemptId`, `actionType`, `reason`, `status`, `createdAt`

No new migrations were created.
No enum values were added.
No field types were modified.

The `TransactionService` query to `findByIdForAttempt` was enhanced to select additional transaction fields (`amount`, `currency`) and count failed attempts, but this is a projection change only—no schema migration.

## 13. Architecture clarity

### Responsibility boundaries

**RecoveryPredictionService**
- Estimates recovery success probabilities for each candidate action
- Internal to 6.5.1; unchanged in 6.5.3

**RecoveryDecisionPolicy (6.5.2)**
- Evaluates ML predictions against business safety rules
- Ranks and selects the best valid candidate
- Falls back to Phase 1 rule engine when ML cannot decide
- Returns metadata-rich decision result

**TransactionService (updated in 6.5.3)**
- Invokes policy instead of engine directly
- Builds prediction context from transaction data
- Persists the selected action using Phase 1 mechanism

**RecoveryExecutionService (unchanged)**
- Executes the recommended action
- No knowledge of ML or policy; continues to work as-is

## 14. Dependency injection pattern

`TransactionService` constructor now accepts:
```javascript
constructor(
  transactionRepository,
  recoveryDecisionEngine = new RecoveryDecisionEngine(),
  predictionService = new RecoveryPredictionService(),
  decisionPolicy = new RecoveryDecisionPolicy(predictionService, recoveryDecisionEngine)
)
```

- All dependencies are optional with sensible defaults.
- Tests can inject mocks.
- Application creates defaults if not supplied.
- `app.js` supports optional injection via `createApp` parameters.

## 15. Backward compatibility

The integration is fully backward compatible:

- Existing tests continue to pass.
- Phase 1 recovery behavior is preserved as the fallback.
- All validation and safety rules remain in place.
- Schema is unchanged.
- Execution path is unchanged.

If ML integration is disabled in the future, the fallback to `RecoveryDecisionEngine` is immediate and transparent.
