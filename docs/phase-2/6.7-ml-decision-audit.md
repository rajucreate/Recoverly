# Phase 2 Task 6.7: ML Decision Audit & Observability Layer

## 1. Purpose & Scope

The **ML Decision Audit & Observability Layer** provides a structured, immutable audit record for every recovery decision produced by the Recoverly intelligence system. 

It establishes decision accountability, forensic explainability, and observability without altering production execution behavior, modifying database schemas, or executing recovery actions.

---

## 2. Core Architectural Principles & Isolation

- **Non-Execution Boundary:** The audit layer is purely observational. It has zero execution capabilities, never calls payment providers, and never initiates payment attempts.
- **Decision Invariance:** The audit layer records decisions as delivered by `RecoveryDecisionPolicy`; it never overrides, mutates, or second-guesses the selected action.
- **Execution Service Independence:** `RecoveryExecutionService` remains the sole execution engine in Recoverly, completely decoupled from audit generation.
- **No Database Migrations:** Audit records are generated as structured, self-contained objects in memory and via structured API/logging artifacts. No Prisma schema changes or relational database column additions are introduced in Task 6.7.
- **Deterministic Recording:** Identical decision contexts and outcomes produce identical structured audit records.

---

## 3. Audit Record Schema

Each decision produces an immutable audit record matching the `6.7.0` schema specification:

```typescript
interface DecisionAuditRecord {
  audit_id: string;                      // Unique audit identifier (UUID with 'audit_' prefix)
  audit_schema_version: string;          // '6.7.0'
  decision_timestamp: string;            // ISO 8601 UTC timestamp
  correlation: {
    transaction_id: string | null;       // Transaction identifier for cross-table correlation
    attempt_id: string | null;           // Payment attempt identifier triggering the decision
  };
  context: {
    failure_category: string | null;     // TEMPORARY_FAILURE | PAYMENT_METHOD_FAILURE | ...
    payment_method_attempted: string | null; // UPI | CARD | NET_BANKING
    attempt_number: number;              // Current attempt number
    prior_failed_attempt_count: number;  // Prior failed attempts on this transaction
    prior_temporary_failure_count: number;// Prior temporary failures on this transaction
    transaction_amount: number | null;   // Transaction amount
    currency: string | null;             // Currency code (e.g. 'INR')
    has_failure_reason: boolean;         // Whether raw failure reason was present
  };
  candidates: Array<{
    action_type: string;                 // RETRY | ALTERNATE_METHOD | CUSTOMER_ACTION | ESCALATE
    ml_probability: number | null;       // Predicted recovery probability (null if rule fallback)
    is_safe: boolean;                    // Whether candidate passed policy safety checks
    rejection_reason: string | null;     // Rejection reason enum if unsafe, else null
  }>;
  rejected_candidates: Array<{
    action_type: string;
    ml_probability: number | null;
    rejection_reason: string;            // Specific safety constraint violated
  }>;
  selected_action: string;               // Chosen action (RETRY | ALTERNATE_METHOD | ...)
  decision_source: 'ML' | 'RULE';        // Strategy delivering the decision
  decision_reason: string;               // Descriptive explanation of selection
  selected_probability: number | null;   // ML probability of selected action (null for RULE)
  fallback: {
    is_fallback: boolean;                // True if decided via Phase 1 rule fallback
    fallback_reason: string | null;      // MODEL_UNAVAILABLE | INVALID_PREDICTION | NO_SAFE_CANDIDATE
    fallback_error: string | null;       // Underlying error message if exception occurred
  };
  versions: {
    model_version: string | null;        // 'phase2-interaction-logistic-v1' or null
    feature_schema_version: string;      // '6.3.1'
    feature_pipeline_version: string;    // '1.0.0'
    policy_version: string;              // '6.7.0'
    audit_schema_version: string;        // '6.7.0'
  };
  performance: {
    decision_latency_ms: number;         // End-to-end decision latency in milliseconds
  };
}
```

---

## 4. ML vs RULE Fallback Representation

### 4.1 ML Decision Representation
When the model evaluates candidates successfully and at least one candidate satisfies all business safety rules:
- `decision_source`: `'ML'`
- `selected_probability`: numeric value in `[0.0, 1.0]` (e.g., `0.85`)
- `fallback.is_fallback`: `false`
- `fallback.fallback_reason`: `null`
- `versions.model_version`: `'phase2-interaction-logistic-v1'`
- `candidates`: contains all 4 candidate actions with their respective ML probabilities and safety classifications.

### 4.2 RULE Fallback Representation
When ML inference fails (missing model, schema mismatch), predictions are malformed, or all ML candidates violate safety constraints:
- `decision_source`: `'RULE'`
- `selected_probability`: `null`
- `fallback.is_fallback`: `true`
- `fallback.fallback_reason`: one of `'MODEL_UNAVAILABLE'`, `'INVALID_PREDICTION'`, or `'NO_SAFE_CANDIDATE'`
- `fallback.fallback_error`: captured error message if an exception was thrown
- `versions.model_version`: `null`
- `decision_reason`: deterministic reasoning from Phase 1 `RecoveryDecisionEngine`

---

## 5. Safety Constraint & Rejection Auditing

The audit service classifies why any candidate was disqualified from selection:
- `RETRY_NOT_APPLICABLE_FOR_CATEGORY`: `RETRY` candidate on non-temporary failure categories.
- `RETRY_LIMIT_EXCEEDED`: `RETRY` candidate when prior temporary failures reached `RETRY_LIMIT = 2`.
- `NO_SAFE_ALTERNATE_METHOD`: `ALTERNATE_METHOD` when no different payment method is available.
- `ACTION_ALREADY_EXECUTED`: Candidate action was already executed on this transaction attempt.
- `TRANSACTION_NOT_FAILED`: Transaction status is not in `FAILED` state.

---

## 6. Security & Privacy Considerations

- **No Raw Sensitive Data:** Audit records do not store card PANs, CVVs, bank account numbers, or user PII.
- **Deterministic Redaction:** Categorical enums (`payment_method`, `currency`) and aggregated numerical counters are stored without customer identifiers.
- **Correlation Integrity:** Correlation relies on opaque system UUIDs (`transaction_id`, `attempt_id`).

---

## 7. What is Intentionally NOT Persisted in 6.7

In strict adherence to Phase 2 non-disruptive design principles:
- **No Database Schema Alterations:** `schema.prisma` remains untouched. No audit tables or JSON columns are added to PostgreSQL.
- **In-Memory Ring Buffer:** `RecoveryDecisionAuditService` maintains an in-memory ring buffer (default 1,000 records) with query, filtering, and eviction support for real-time observability and testing.
- **Zero External Telemetry Dependencies:** No external log shipping agents, Datadog/Kafka dependencies, or telemetry agents are introduced.
