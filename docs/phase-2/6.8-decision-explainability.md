# Phase 2 Task 6.8: Explainability & Decision Transparency

## 1. Purpose & Scope

The **Decision Explainability & Transparency Layer** provides deterministic, transparent, and auditable explanations for every recovery recommendation produced by the Recoverly intelligence system.

It translates internal machine learning scores, candidate rankings, and rule fallback justifications into both **structured machine-readable objects** and **human-readable narrative text**.

---

## 2. Downstream Architecture & Isolation

The explainability layer is strictly downstream of the decision engine:

```text
Prediction (RecoveryPredictionService)
    ↓
RecoveryDecisionPolicy (Filters & Ranks Candidates)
    ↓
Decision & Audit Context (buildDecisionAuditRecord)
    ↓
RecoveryDecisionExplanation (Structured + Human Explanation)
    ↓
Payment Execution (RecoveryExecutionService) [Unchanged]
```

### Isolation Guarantees:
- **Zero Decision Interference:** The explanation layer never selects, modifies, or overrides recovery decisions.
- **Zero Execution Power:** It does not invoke payment providers or execution services.
- **No Schema Changes:** `schema.prisma` and database tables remain untouched.
- **Strictly Downstream:** It interprets existing decision facts without running secondary ML inferences or alternate rule engines.

---

## 3. Structured Explanation Schema (`version: 6.8.0`)

```typescript
interface DecisionExplanation {
  explanation_schema_version: string;    // '6.8.0'
  selected_action: string;               // Chosen action: RETRY | ALTERNATE_METHOD | CUSTOMER_ACTION | ESCALATE
  decision_source: 'ML' | 'RULE';        // Source mechanism
  summary: string;                       // Brief summary statement
  human_readable_text: string;           // Formatted narrative explanation
  reasons: Array<{
    type: 'MODEL_RANKING' | 'SAFETY_VERIFICATION' | 'SAFETY_REJECTION' | 'RULE_FALLBACK' | 'RULE_DETERMINATION';
    message: string;                     // Detailed explanation of this reason factor
    action?: string;                     // Action associated with reason
    predicted_recovery_probability?: number | null; // Estimated probability
    fallback_reason?: string | null;     // Fallback reason code if applicable
    rejection_reason?: string | null;    // Safety rejection code if applicable
  }>;
  candidate_comparison: Array<{
    action: string;                      // Candidate action type
    predicted_recovery_probability: number | null; // Predicted probability
    rank: number | null;                 // Rank by probability (1-4)
    is_safe: boolean;                    // Safety compliance
    rejection_reason: string | null;     // Constraint violated if unsafe
    status: 'SELECTED' | 'REJECTED_BY_SAFETY' | 'CONSIDERED_LOWER_PROBABILITY';
  }>;
  rejected_candidates: Array<{
    action: string;
    predicted_recovery_probability: number | null;
    rejection_reason: string;
    explanation: string;                 // Plain-language safety constraint description
  }>;
  fallback: {
    is_fallback: boolean;
    fallback_reason: string | null;      // MODEL_UNAVAILABLE | INVALID_PREDICTION | NO_SAFE_CANDIDATE
    fallback_error: string | null;
    rule_reason: string;
  } | null;
  context_summary: {
    failure_category: string | null;
    payment_method_attempted: string | null;
    attempt_number: number;
    prior_failed_attempt_count: number;
    prior_temporary_failure_count: number;
  };
  versions: {
    model_version: string | null;
    feature_schema_version: string;
    feature_pipeline_version: string;
    policy_version: string;
    explanation_schema_version: string;
  };
}
```

---

## 4. Explanation Semantics

### 4.1 ML Decision Explanations
When the ML model recommends an action:
1. **Ranking & Relative Probability:** Outlines all candidates, ordered by predicted recovery probability.
2. **Safety Verification:** Validates why the chosen candidate was cleared by business safety rules.
3. **Candidate Elimination:** Explicitly accounts for why higher or lower alternatives were rejected or deprioritized.
4. **Probability Nuance:** Probabilities are expressed as estimated likelihoods (e.g. *"85.76% estimated recovery probability"*), explicitly avoiding claims of 100% certainty.

### 4.2 RULE Fallback Explanations
When the policy falls back to Phase 1 rules:
1. **Fallback Cause:** Explains why ML was skipped (`MODEL_UNAVAILABLE`, `INVALID_PREDICTION`, or `NO_SAFE_CANDIDATE`).
2. **Deterministic Logic:** States the exact rule-based justification from `RecoveryDecisionEngine` (e.g., *"retry limit reached"*, *"payment method failure requires alternate method"*).
3. **Safety Constraint Context:** If candidates were evaluated before safety disqualification (such as exhausted retries), their rejection codes are preserved.

---

## 5. Security, Privacy & Redaction

- **No Cardholder Data (CHD):** PANs, CVVs, expiry dates, passwords, and tokens are never included.
- **Redacted Context Summary:** Only business metadata (failure categories, payment methods, attempt counts) is present.
- **Zero Coefficient Exposure:** Raw regression weights and linear intercepts are not exposed in human narratives.
