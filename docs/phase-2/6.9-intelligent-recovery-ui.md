# Phase 2 Task 6.9: Intelligent Recovery UI Integration

## 1. Purpose & Scope

**Task 6.9** connects the Phase 2 Machine Learning intelligence and explainability layer to the Recoverly React frontend application.

It enables operators to view:
- Machine Learning recommendations vs Rule Fallbacks.
- Estimated recovery probabilities with uncertainty framing.
- Plain-language narrative explanations of recovery choices.
- Candidate action rankings and comparison breakdowns.
- Specific business safety constraints and rejection reasons.

All features strictly adhere to Phase 2 non-intrusive architecture and zero-schema-change principles.

---

## 2. Architecture & Data Flow

```text
Payment Simulation / Attempt Triggered
    ↓
POST /api/transactions/:id/attempts
    ↓
TransactionService.createPaymentAttempt()
    ├── RecoveryDecisionPolicy.decide()
    ├── RecoveryActionRepository.create() [Persisted: actionType, reason]
    └── explainDecision() [Generated ephemeral explanation]
    ↓
Response Payload: { attempt, recoveryAction, explanation }
    ↓
TransactionDetailPage.jsx (Maintains ephemeral explanation state)
    ├── RecoveryActionPanel.jsx (Embeds DecisionExplanationCard)
    └── PaymentAttemptForm.jsx (Displays immediate intelligence in attempt result)
    ↓
Operator clicks "Execute recovery"
    ↓
POST /api/transactions/:id/recovery/execute
    ↓
RecoveryExecutionService.execute() [Unchanged Execution Boundary]
```

## 4. Frontend Components

1. **`DecisionExplanationCard.jsx` (`frontend/src/components/recovery/`):**
   - **Decision Badge:** Visual pill clearly designating `ML Recommendation` (green) or `Rule Fallback` (amber).
   - **Probability Display:** Highlights estimated recovery percentage (e.g. `85.8%`) with an explicit disclaimer: *"Estimated recovery probability is a model prediction derived from historical failure patterns, not an outcome guarantee."*
   - **Narrative Explanation:** Formats plain-language description explaining the rationale.
   - **Fallback Banner:** When fallback occurs, renders a warning callout detailing the fallback reason code and Phase 1 rule determination.
   - **Safety Constraints Box:** Lists any candidate actions disqualified by safety rules (e.g. retry limit reached).
   - **Candidate Comparison Accordion:** Collapsible table showing candidate actions, estimated probabilities, ranks, statuses, and safety checks.

2. **`RecoveryActionPanel.jsx` (`frontend/src/components/recovery/`):**
   - Receives `explanation` as an optional prop.
   - When present, embeds `DecisionExplanationCard`.
   - When absent, falls back gracefully to standard `<p className="recovery-reason">{action.reason}</p>`.
   - Leaves the "Execute recovery" workflow completely unchanged.

3. **`PaymentAttemptForm.jsx` (`frontend/src/components/transactions/`):**
   - Updates the simulation `.attempt-result` card with the decision badge, probability tag, and human explanation.

4. **`TransactionDetailPage.jsx` (`frontend/src/pages/`):**
   - Coordinates state between payment simulation attempts and the recovery action panel.

---

## 5. Non-Persistence Limitation & Graceful Degradation

- **Database Invariance:** In adherence to Phase 2 constraints, `schema.prisma` was not modified.
- **Ephemeral Availability:** The rich `explanation` object is received immediately upon recording a payment attempt via `POST /attempts`.
- **Page Reload Behavior:** On full page reload, `GET /api/transactions/:id` returns only persisted `RecoveryAction` database records. The frontend gracefully falls back to displaying the persisted `action.reason` without crashing or inventing mock data.

---

## 6. Execution Boundary & Safety Confirmations

- **Strictly Downstream:** The explanation components never call payment gateways or trigger payment attempts.
- **No Direct Execution:** Recovery execution remains solely governed by `RecoveryExecutionService` via `POST /api/transactions/:id/recovery/execute`.
